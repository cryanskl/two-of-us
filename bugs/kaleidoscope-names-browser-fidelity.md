# 万花筒名字：程序化标题焦点与组合状态可见性

- 发现日期：2026-07-25
- 影响：桌面调参态与完成态
- 状态：已修复并补回归测试

## 现象

真实 Chrome 首轮验收发现两处可见偏差：

1. 进入完成态后，脚本为读屏顺序把焦点移到 `h1`，但通用
   `:focus-visible` 规则把标题绘制成一块巨大的双层焦点框。
2. 调参态的组合摘要只作为图案的 `figcaption` 出现在右栏下方。在桌面低高度视口
   中，两条分轴状态可见，但组合结论可能落到首屏之外。

## 原因

- `tabindex="-1"` 标题只承担阶段切换后的程序化焦点，不是可操作控件；它不应复用
  按钮、滑块等交互元素的强焦点外观。
- 图案题注同时承担无障碍命名和可见组合摘要，导致信息位置受大尺寸方形 Canvas
  牵制。

## 解决

- 保留标题程序化焦点与读屏顺序，单独移除 `.phase > h1:focus` 的轮廓和阴影；
  按钮与滑块继续使用高对比度 `:focus-visible` 样式。
- 在控制栏状态列表后加入可见 `.combined-summary`，只消费核心公开视图的
  `view.summary`；图案 `figcaption` 保留为屏幕阅读器可见的图形名称。
- 同次修复给 Canvas 延迟绘制增加 `isConnected` 代际检查，并把上下文获取和实际
  绘制失败统一降级到 CSS 图案。

## 回归

定向测试冻结标题焦点、组合摘要、Canvas 断连保护和绘制失败降级。真实 Chrome
复验确认：组合摘要位于左栏状态下方；完成态标题仍获得焦点，但 computed style
为 `outline: none`、`box-shadow: none`；交互控件焦点样式不变。

## 可复用结论

程序化焦点的语义目的与键盘可操作控件的视觉目的并不完全相同。渐进式阶段页面应
分别验证“焦点落点正确”和“焦点外观适合该元素”；重要状态也不应只依附于尺寸可能
超出首屏的装饰图形题注。
