# Token 守卫的双角色协作交接

适用于流水线、传球、装货、接力、接物和节奏同步等“角色 A 发出对象，角色 B 在抵达前准备接收位置”的同屏合作玩法。

## 两位玩家必须各自拥有不可替代的变量

合作感不能只靠两套按键。规则状态至少要把权力拆开：发送者拥有内容与发送通道，接收者拥有抵达位置；任何一方都不能直接改写另一方的变量。

一次成功交接应同时检查：

1. 发送内容是当前目标；
2. 发送通道与接收位置一致；
3. 检查发生在对象抵达的结算时刻。

内容错误但接稳、内容正确但漏接应是两个可区分结果。两者都作用于共享容错，不建立个人失误榜，避免合作玩法退化为责怪工具。

## 动画只呈现已经冻结的 flight

dispatch 时把 `ingredientId`、`lane` 和单调递增 `token` 固化为 flight。飞行期间可以允许接收者继续移动，但不能让发送者换掉在途内容。CSS 动画只读取 flight，不决定结果。

结算函数必须同时收到当前 state 与回调 token：

- token 不匹配时返回原状态；
- 已离开 flight 阶段时返回原状态；
- 只有当前 token 可以推进一次。

这样 animationend、定时器 fallback、页面切后台和重复事件可以并存，而不会重复加分或重复扣容错。

## 计划、输入和结算分三层

- 计划层：安全随机生成固定订单与每阶段候选，进入 reducer 前校验、复制、冻结；
- 输入层：鼠标、触控、键盘只映射到 `moveDispatcher`、`movePlate`、`dispatchIngredient`；
- 结算层：`resolveDelivery` 只读冻结 flight 和抵达时 plate，不访问 DOM 或时钟。

浏览器使用 `crypto.getRandomValues` 与拒绝采样；测试注入确定性索引。安全随机不可用时明确停在 intro，不回退到可预测随机。

## 阶段反馈要有明确所有权

同一次 transition 可能同时产生“最后一次错误食材”和“达到失败终局”。渲染时应先看 phase，再看普通 event；否则局部事件会覆盖更重要的阶段信息。

焦点和 live region 也遵循同一原则：新阶段显式接管目标，离开阶段时清除旧播报。不要用“这次变化很重要”代替“当前阶段确实存在可聚焦主按钮”。

## 验证方法

- reducer 测试覆盖正确、错接、漏接、三次失败、四单成功与过期 token；
- 浏览器刻意先错接一次、漏接一次，再在只剩一次容错时完成全局；
- 交替使用按键和按钮，并验证 flight 期间接收者仍可移动；
- 同时触发动画结束与超时回退，确认只结算一次；
- 检查 success / failed / restart 的可见文案、焦点与 live region 一致。

反例是动画结束时直接读取“当前被选中的食材”，或用 CSS 动画次数推导得分。它们会让迟到输入和重复回调改变规则事实。
