# 固定步长柔性约束：先证明公开状态，再谈画面平滑

## 适用范围

适用于两端牵引载荷、绳索、天平、弹簧、拖拽物、航行或其他“输入持续施力 + 多种位置约束”的本地 HTML 游戏。这里的目标不是建立通用物理引擎，而是让一个小型玩法在不同刷新率下可重复、可测试。

## 1. 渲染帧不是规则时间

把 `requestAnimationFrame` 的任意 `delta` 直接传进物理会让 60Hz、120Hz、后台恢复和测试环境产生不同轨迹。规则应只暴露固定 `step(state, input)`；浏览器用 accumulator 把帧时间拆成 `1/120s` 子步，并限制单帧最大补步数。

这样“不同帧切片得到相同最终状态”可以用同一批输入直接验证。视图层只决定一帧画几次，不决定规则走多远。

## 2. 多个位置约束会互相破坏

同心牵引同时有世界边界、圆-AABB 碰撞和两条最大长度约束。若迭代顺序是：

```text
碰撞 → 丝带 → 碰撞 → 丝带 → … → 丝带
```

最后一次丝带投影可能把物体重新推入障碍。有限次迭代之后应明确选择公开状态要保证的硬不变量，并做一次最终投影。在本项目里，顺序是：

```text
积分 → 多轮（碰撞 → 丝带）→ 最终碰撞/边界 → 危险与终点判定
```

位置恰好落在切点也不应依赖浮点相等；很小的几何 epsilon 可以让状态稳定留在合法侧，但 epsilon 必须远小于视觉和玩法容差。

## 3. 可解轨迹要观察载荷，不只观察控制端

离散迷宫可以用 BFS 枚举联合位置；连续柔性系统更适合确定性控制器或录制输入轨迹。控制器的 waypoint 必须同时考虑线轴和共享吊坠，因为吊坠有惯性、会滞后，也会被两条线的合力改变路线。

一个有价值的可解性测试至少证明：

- 只调用生产 reducer；
- 从真实出生状态到真实完成态；
- 全程不穿透、不超绳长、不靠重置跳关；
- 至少一次两名玩家同时给出不同方向输入；
- 相同输入序列可在不同渲染帧分组下复现。

## 4. 暂不抽共享引擎

第一款柔性约束游戏只在作品目录内保留固定步和碰撞实现。等灯塔航行或双人天平出现后，再比较它们真正共有的是 accumulator、向量工具、碰撞还是状态机；第二个使用者出现前抽象出的“通用物理层”大概率只是当前玩法常量的伪装。
