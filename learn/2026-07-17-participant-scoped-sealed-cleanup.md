# 密封状态按参与者作用域清理

## 1. 清理作用域不能大于状态所有者

一轮秘密提交属于“房间中的一组冻结参与者”，不只是属于房间。成员离开时直接 `clearRoom` 虽然简单，却会把无关访客的退出放大成两位玩家的状态丢失。

清理 API 应与状态所有权对齐：`clearMember(roomId, memberId)` 只删除包含该成员的轮次；房间为空时才使用 `clearRoom`。这个原则同样适用于协作锁、回合计时器、画布缓存和上传会话。

## 2. 产品容量与底层健壮性要同时成立

情侣体验的产品房间明确只有两席，因此根运行时应在加入 Gate 直接返回 `ROOM_FULL`。但底层 registry 仍要正确处理第三人或更大容量，因为测试、自定义实例、旧客户端和未来观战功能都可能产生不同成员集合。

容量限制减少可达错误路径；参与者感知清理保证即使错误路径重新变得可达，状态也不会被无关生命周期误删。两者不是重复防御。

## 3. 失败案例必须验证后续是否还能完成

只断言“第三人离开后 registry 还有一条记录”证据不足。更强的回归测试应按真实序列继续让 B 提交，并断言 A/B 收到完整的同一结果；这样同时证明第一份数据仍在、参与者顺序未变、完成标记正确。

冻结参与者离开的反向测试也必须存在：新人不能继承旧答案，旧 round 应重新开始或被成员变化 Gate 拒绝。
