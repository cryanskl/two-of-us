# 正交离散合作：把颜色显示与成功规则分开

适用范围：两人分别控制不同参数的同屏合作玩法，例如色相/明度、方向/力度、电压/频率、温度/时间、横向/纵向定位。尤其适合需要 `file://` 直开、可重放测试和无颜色依赖反馈的轻量 HTML。

## 核心结论

“两个人都有按钮”不等于“两个人都不可替代”。如果四个按钮最终都写入同一个自由值，一位熟练玩家仍可包办全部操作。更稳的合作边界是让每位玩家只拥有一个正交状态轴：

```text
玩家 1 输入 → hueIndex
玩家 2 输入 → lightnessIndex

成功 ⇔ hueIndex === targetHueIndex
    且 lightnessIndex === targetLightnessIndex
```

两条轴互不写入，因此从同一旧状态出发，先调色相再调明度与先调明度再调色相应得到同一最终状态。这条交换律既证明输入职责没有串扰，也能作为稳定的单元测试。

## 规则层只保存整数索引

颜色值不应成为胜负真相。CSS 颜色语法、显示器色域、浏览器实现与系统色彩管理都可能不同；如果规则直接比较渲染后的字符串、RGB 浮点值或截图像素，就会把显示差异误当作玩法差异。

权威状态只保存离散索引：

```js
{
  hueIndex: 8,
  lightnessIndex: 2,
  targetHueIndex: 1,
  targetLightnessIndex: 7
}
```

渲染层再把索引映射为颜色 token：

```text
索引 → 固定 hueDegrees / lightness 表
     → 浏览器支持时输出 OKLCH
     → 否则输出 HSL
```

这样 OKLCH 与 HSL 可以看起来略有不同，却必须产生相同的回合结果、移动次数和完成记录。色彩映射属于展示降级，不属于规则降级。

## 环形轴与线性轴要分别建模

色相是环，明度是线：

- 环形轴在末端继续前进会回到起点；方向提示应使用最短环形距离，并冻结正好半圈时的平局方向；
- 线性轴在两端钳制；撞到边界的无效动作不应增加移动计数；
- 两类轴不能共用一个未经区分的 `clamp()` 或 `%`，否则一端会出现错误的绕回或卡死。

反例：把所有轴都写成 `(index + direction + count) % count`，会让“明度再亮一点”从最亮突然跳到最暗。把所有轴都钳制，则色相从第 12 格无法顺时针回到第 1 格。

## 反馈不能只靠颜色

目标色与当前色即使肉眼很明显，也仍要公开结构化反馈：

- 当前第几格、目标第几格；
- 还差几格；
- 应向哪个方向移动；
- 单轴命中时显示“色相已经合拍”或“明度已经合拍”；
- 双轴命中后才出现文字结果与下一步按钮。

这同时解决三件事：色觉差异、低质量屏幕和用户不知道“差在哪里”。视觉色块是情绪反馈，刻度与文字才是可操作反馈。

## 倒计时也应离散化

规则使用整数 tick，rAF 只累计真实经过时间并消费整数 tick：

```text
frame elapsed → accumulator
accumulator / tickMs → whole ticks
whole ticks → reducer
```

不要把 `performance.now()`、CSS 动画进度或小数秒直接写进 reducer。页面隐藏、窗口失焦或帧间隔异常时暂停并清 accumulator，恢复后不补跑后台时间。这样 60Hz、120Hz 与偶发掉帧不会改变规则结果。

## 最小验证矩阵

1. 两条轴各自只改自己的索引和移动次数；
2. 两种输入顺序交换后状态逐字段相同；
3. 环形轴首尾绕回，线性轴两端钳制；
4. 只命中一条轴时不能完成；
5. 最后一个有效动作只追加一次成功记录；
6. 超时不追加色笺，重试保持同一目标；
7. OKLCH 与 HSL token 不同，但规则结果完全相同；
8. 文本、刻度和形状足以在不辨颜色时完成；
9. 两个不同 `pointerId` 能同时保留两个玩家的按压态；
10. 320px 无横向溢出，触控目标不缩到规格以下；
11. 背景资源失败时，纯色降级仍可读；
12. 正常 `file://` 不产生网络、存储或权限请求。
