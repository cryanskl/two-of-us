# 双边界唯一接取区间：邻接负样本、操作顺序与合作必要性

适用于两人分别控制共享范围两端的轻量合作玩法，例如接雨、撑伞、调焦、托盘、扫描窗或安全区。

## 核心模型

把舞台离散为 `N` 道，权威状态只保存闭区间 `[left, right]`，并始终维持：

```text
0 ≤ left ≤ right < N
```

左席只能改变 `left`，右席只能改变 `right`。这样每位玩家权限都很小，但两人的动作共同定义一个对象。`N = 7` 时只有 `7 × 8 / 2 = 28` 个合法区间，足以穷举，不需要用随机试跑替代证明。

## 用邻接负样本制造唯一解

每波在目标端点 `L`、`R` 各放一个正目标，并在存在时于 `L - 1`、`R + 1` 放负目标。结算顺序应先检查污染，再检查漏接：

1. 区间包含任一负目标：失败；
2. 没有污染，但缺任一正目标：失败；
3. 两个正目标都在区间内且没有负目标：成功。

因此：

- 收窄任一端会漏掉正目标；
- 扩宽任一端会接到紧邻负目标；
- 唯一成功区间恰为 `[L, R]`。

实现后应枚举全部 28 个区间，断言每波恰有一个成功项，且它等于配置目标。这个 oracle 比截图、动画位置或人工“看起来合理”稳定得多。

## 边界相遇让操作顺序也成为合作

若移动规则禁止 `left > right` 或 `right < left`，两端相遇时动作会被合法钳制。目标需要整体向右移动时，右席必须先让出空间，左席才能继续推进；整体向左则相反。

真实 Chrome 实玩中，最后一波目标为 `[5, 6]`，默认区间为 `[2, 4]`。若左席先连续右移三次，第三次会在 `[4, 4]` 被钳制，随后即使右席移动，最终也只得到 `[4, 6]` 并接到邻接灰滴。改为右席先移动到 `6`，左席再移动到 `5`，即可成功。

这类顺序约束应保持可解释：

- 无效动作不增加 revision；
- 控件在边界处同步禁用；
- 失败反馈指出具体污染道或漏接侧；
- 重试恢复统一默认区间，避免旧边界制造隐形状态。

## 证明双方不可替代

“有两个控制区”不等于“必须两个人”。最低限度要补两类测试：

1. 穷举每波全部区间，证明配置唯一解；
2. 固定其中一席为默认边界，只允许另一席操作，证明完整关卡序列不可完成。

第二类证明要覆盖整条固定路线，而非只挑最难的一波。不同波次应让左右端点分别出现内移、外移和边界值，避免某一席长期无事可做。

## 表现层边界

规则只处理道号、区间、正负目标和整数 tick。水滴下落比例、云朵宽度、背景与材质均由公开 view 派生；生成式图片只承担气氛，不能编码目标答案。这样 `file://`、reduced motion、窄屏重排或资产加载失败都不会改变结算。
