# 浏览器 pthread 语音构建要验证整条运行契约

## 适用范围

C/C++ 推理引擎通过 Emscripten 编译，在应用 Worker 内同步调用，并由引擎继续创建 pthread 子 Worker。

## 稳定结论

“WASM 能实例化”不等于“真实推理能完成”。发布门禁至少覆盖四层：

1. **文档隔离**：顶层响应具备 COOP/COEP，运行时确认 `crossOriginIsolated` 和 `SharedArrayBuffer`；
2. **Worker 资源策略**：被当作嵌套线程入口的引擎 JS 自身也要满足隔离与同源资源策略；
3. **绑定边界**：C++ 通过 `Module` 读取的堆视图必须显式导出，结构化错误要跨 Worker 协议保留；
4. **计算后端**：CMake 必须识别 wasm 目标并编入对应量化内核，同步推理前应预热线程池。

## 为什么单元测试不够

虚拟 Worker 可以验证消息格式、URL 白名单和释放顺序，却不会运行浏览器安全策略、Emscripten 生成 runtime、真实共享内存或 148 MiB 模型。真实 Gate 应使用固定、非私人 WAV，并记录：格式、样本数、完整文本、推理耗时、总耗时、隔离状态和模型 doctor 结果。

## 模型与仓库资产的升级边界

用户目录只安装大模型 artifact；JS/WASM 属于仓库资产。receipt 可保留完整 manifest 哈希做来源记录，但可用性应由协议版本和已安装 artifact 清单决定，否则任一浏览器资产重建都会迫使用户重复下载未变化的大模型。

## 反例

- 只看到模型初始化成功就宣称语音可用；
- 只给 HTML 加 COEP，不检查 Worker 脚本响应；
- 相信 CMake 的默认处理器字符串会选择 wasm 后端；
- 在线程首次使用时动态创建 Worker，然后在同步 C++ 调用中等待它；
- 用整个 manifest 哈希替代 artifact 级兼容判断。

## 推荐验证顺序

先跑生成物哈希和协议测试，再在 Chrome 中依次验证模型初始化、固定短样本、接近产品上限的完整样本、桌面/移动界面，最后由真人明确授权完成麦克风权限和两轮交互。
