# 双人席位 Gate 与玩法状态分层

## 1. 共享“谁能玩”，不要共享“怎么玩”

多个双人 C 级作品都需要同一组成员判断：只取前两席、识别当前 host、第三人退出、成员或 host 变化后重置。这些是传输协议边界，适合集中到 `two-player-membership.js`。

比分、题目、棋盘和回合转换仍属于各作品。把它们抽进公共 helper 会迫使猜拳、四子棋和问答共享不存在的状态模型，反而降低可测试性。

## 2. 内部迁移也要保留外部 API

现有 app 与协议测试都从各作品的 `protocol.js` 导入 `reconcileMembership`。迁移时由协议文件把共享函数别名导出为旧名称，调用方无需同时修改。

这种“先保持接口、替换实现”的方式让重构提交只表达去重，不混入页面或行为变化；后续新作品可以直接导入共享名称。

## 3. Reset 需要同时比较席位和 host

成员 ID 顺序不变并不代表局面可继承：host 角色迁移后，权威状态的发布者已经改变，也必须重置。反过来，新成员占据第二席，即使 host 没变，也不能继承前任的棋盘、答案或比分。

因此 helper 分别比较前后席位 ID 序列与已知 host ID；任一变化都设置 `shouldReset`。玩法层收到该信号后负责清空自己的全部私密和公开状态。
