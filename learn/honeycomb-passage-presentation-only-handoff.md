# 热座交接应是展示状态，而不是规则行动

## 可复用结论

同设备热座游戏需要“把页面交给下一位”时，交接 gate 应留在 UI 层：

1. 合法规则行动先完整提交 reducer，得到下一位玩家的权威 view；
2. UI 立刻进入 `handoffPending`，冻结棋盘和模式按钮；
3. gate 公开下一位名字并接管焦点；
4. 确认交接只清除 `handoffPending`，不再 dispatch reducer；
5. 关闭 gate 后才把焦点交给新回合标题。

## 为什么不能放进 core

如果把“确认拿好了”建模为规则 action，会产生一个没有玩法意义的额外 revision：

- history、回放和回合统计必须识别并忽略它；
- 重复点击或双击可能伪造额外行动边界；
- 规则核心开始依赖页面是否需要遮挡；
- CLI、测试或未来双设备呈现被迫模拟同一 UI 仪式。

把交接留在展示层后，core 只回答“谁行动、哪些格合法、行动后是什么状态”，不同
外壳可以选择 gate、屏幕遮挡或直接切换，而不改变同一份回放。

## 仍需冻结的边界

展示状态不等于可以随意点击。gate 出现时必须同时：

- 禁用全部 cell button 和移动/封蜡按钮；
- 把焦点移到唯一确认按钮；
- 保留刚完成行动的公开状态文字；
- 确认函数中禁止调用 reducer/dispatch；
- 确认后把焦点移到回合标题，并通过 live region 宣布轮到谁。

`honeycomb-passage` 的 UI 契约用静态测试锁定这些边界，Chrome 完整对局再证明每个
合法行动都必须经过一次交接，而交接确认不会消耗封蜡、移动棋子或增加 history。
