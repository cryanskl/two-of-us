# 运行时兼容性不等于当前内容身份

## 适用范围

同一台电脑可能同时存在多个 checkout、worktree、分支或已更新目录，而作品启动器会扫描固定端口并复用已有本地 HTTP 进程。

## 稳定结论

### 1. 身份至少分三层

| 层 | 要证明什么 | 典型字段 |
| --- | --- | --- |
| 服务类型 | 不是碰巧占端口的普通 HTTP 服务 | 专用响应头、loopback、同源、拒绝重定向 |
| 协议兼容 | 客户端与服务能使用同一份 API | protocol version、schema、目标 ID |
| 内容身份 | 服务提供的正是当前启动器所属内容 | 当前 checkout 的 deterministic content identity |

前两层都通过，仍可能打开另一 worktree 的旧页面。协议版本只应在不兼容变更时更新，不能承担每次内容变化的身份职责。

### 2. 路径身份不够

对绝对根路径做哈希可以区分两个 worktree，却不能识别同一路径在 `git pull`、切分支或修改文件前启动的旧进程。进程启动 nonce 只能证明“同一个进程”，也不能让新的启动器知道该进程内容是否匹配。

内容身份必须随实际可服务内容变化。可选做法按可靠性排序：

1. 对发布清单及清单覆盖的文件内容做 SHA-256；
2. 对 catalog、lockfile、共享运行时和所有已安装作品文件做规范化内容哈希；
3. 仅使用 Git commit 时，必须另行处理 dirty worktree 与无 `.git` 的分发包。

不要把绝对本机路径直接暴露到 health；如果路径参与区分，也只返回不可逆摘要。

### 3. 复用是优化，不应改变正确性

探针无法证明内容身份时，正确退路是另启可用端口，而不是复用“看起来兼容”的进程。这样最坏结果是多一个本地服务，不会把用户带到另一份作品内容。

### 4. 测试必须跨根目录

只在同一 `projectRoot` 连续启动两次，只能证明复用机制能工作。完整矩阵应至少包括：

- 同内容、同协议：复用；
- 不同内容、同协议：拒绝复用；
- 同内容、不同协议：拒绝复用；
- 外来服务或重定向：拒绝复用；
- 当前 checkout 有未提交改动：按产品明确策略复用或拒绝，不能静默猜测。

测试的另一端应真正返回不同静态标记；只改变 health 的无关字段不足以证明最终页面来自哪个根目录。

## 反例

- 用 `x-app: 1` 加 schema 校验就声称“当前项目已经在运行”；
- 用 worktree 绝对路径作为公开 health 字段；
- 每次内容变化都提升 protocol version；
- content identity 只覆盖 catalog，忽略入口、脚本、样式与共享运行时；
- 发现不匹配后终止陌生进程，而不是保留其所有权并选择新端口。

## 验证方法

1. 准备两个 schema 与协议完全一致、静态入口含不同 marker 的临时根目录；
2. 先启动根 A，再从根 B 运行启动器；
3. 断言根 B 不复用 A 的端口，最终入口返回 B 的 marker；
4. 再从根 A 启动第二次，断言它仍能复用 A；
5. 修改清单覆盖的任一文件，断言 content identity 随之变化；
6. 停止各自所有者后确认端口释放，避免把内容身份修复变成生命周期耦合。
