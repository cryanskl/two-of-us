# 开源候选要固定来源谱系，不只固定项目名

## 问题

GitHub 仓库名和 fork 标记都不是稳定的一手来源证据。仓库可能被删除、转移、脱离 fork 网络，或在保留原提交与 LICENSE 的同时由另一个账号继续发布。只记录 `owner/repo + MIT`，后续很难判断真正的作者、借鉴版本和许可证是否仍可验证。

## 最小证据组

准备把一个候选写进规格或作品 README 前，至少固定：

1. 原始或规范仓库的 `owner/repo`；
2. 实际审阅的完整 commit SHA；
3. 该 commit 下的 LICENSE / COPYING / NOTICE 直链；
4. 许可证正文中的版权作者；
5. 实际借鉴的机制，以及明确没有复制的代码、素材和数据；
6. 若通过 fork 发现项目，记录 fork 与原仓库的共同提交边界，但让借鉴链接指回一手来源。

## 删除与替换

上游 404 不等于可以继续沿用旧许可证结论。若没有固定 commit 的可验证快照，应把它降级为历史灵感：保留原名称、复核日期、API/Git 失败事实和“不复制”的决定。为了保持能力地图完整，可以补入同类型且许可证仍可验证的候选，但不能假装二者是同一个项目。

替代项目也要重新检查运行边界。本次生日候选虽然是 MIT，但仍有 Google Fonts、麦克风权限、根路径资源和缺失示例相册；“许可证明确”只解决可用权，不等于已经本地可运行。

## 验证方式

- GitHub Repository API 确认仓库、默认分支与许可证检测；
- `git ls-remote <repo> HEAD` 固定当前 commit；
- Contents API 在该 commit 下读取许可证与 README；
- Trees API 枚举真实文件，源码扫描远程 URL、权限 API 和缺失资源；
- 全仓库搜索旧 owner、失效链接和错误许可证文件名，确保规格与已实现作品同步纠正。
