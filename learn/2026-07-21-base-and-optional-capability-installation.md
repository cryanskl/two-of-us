# 基础依赖与大型可选能力：同一入口、分层承诺

- 日期：2026-07-21
- 适用范围：本地优先仓库中同时存在轻量共享依赖，以及模型、语音引擎或大型素材等按需能力

## 结论

“统一安装”不应被实现成“默认安装一切”。更稳妥的合同是：同一个入口先完成所有作品共享的基础阶段，再枚举缺失的可选能力，由交互用户逐项确认。于是入口统一了，下载许可、磁盘成本和作品可用性仍然分层。

基础阶段成功后必须立即明确报告。随后某个可选能力失败，只让依赖它的 D 级作品暂不可用，不应回滚或谎称 A/B/C 的基础安装失败。反过来，setup 也不能因用户拒绝模型就用非零退出码惩罚一次正常选择。

## 四个稳定边界

### 1. TTY 是大型下载的许可边界

只有 `stdin.isTTY === true && stdout.isTTY === true` 时才发起逐项确认。管道、CI、GUI 包装器或输入重定向环境不得等待回答，更不能把“没有回答”解释为同意；它们应跳过并打印包含能力 ID 的精确后续命令。

显式 `--skip-optional` 比环境猜测更强：仍完成基础依赖，但连能力枚举和状态读取都不执行。这样它既是快速路径，也是“绝不触碰用户能力目录”的可测试合同。

### 2. 安装命令成功不等于能力可用

安装器可能把“用户拒绝”作为正常退出，也可能在写入后遇到损坏或协议不兼容。因此 orchestration 必须在命令结束后重新读取公开 status：只有 `available` 才算 installed；返回 0 但仍 missing 是 skipped；异常、非零或复读失败才是 failed。

这条状态复读原则同样适用于下载器、编译器和外部工具：以最终可消费状态为真相，不以子命令退出码代替领域验证。

### 3. 复用下载器，不复制安全机制

统一 setup 只负责顺序、确认、汇总和退出码。固定 URL、`.part` 临时文件、长度与 SHA-256 校验、原子落盘、receipt、doctor 与 remove 继续由单一能力管理器负责。复制第二套下载逻辑会让许可说明、完整性检查和故障修复立即分叉。

### 4. 内层错误流也属于隐私边界

外层捕获异常并不够：内层 CLI 可能先把完整下载 URL、绝对用户路径、模型文件名或哈希写到真实 stderr，然后才返回非零。调用方应把内层 stderr 隔离到私有 buffer，只提取行首稳定错误码；对外输出能力 ID、稳定码和修复动作，不转发原始正文。

## 反例

- 默认安装全部能力：未来新增模型会无声扩大网络、磁盘和许可成本。
- 页面启动时补下载：用户无法区分“打开作品”和“允许联网写入大文件”。
- 只看子命令退出码：会把拒绝误报为安装完成，或让损坏资产进入运行期。
- catch 后再打印 `error.message`：异常正文可能包含用户目录和带令牌的地址。
- 为每个作品复制安装脚本：相同模型被重复下载，校验和卸载语义逐渐不一致。

## 验证方法

使用依赖注入覆盖 Node/npm gate、空能力、已可用、非 TTY、显式跳过、拒绝、成功、非零、抛错、复读失败与多能力继续处理。特别加入一个恶意内层 CLI：先向 stderr 写入完整 URL、绝对路径与 64 位哈希，再返回非零；外层输出不得包含任何这些内容。

真实烟测使用 `--skip-optional`，确认基础安装、退出码、工作树和最终启动提示，同时避免替用户接受大型模型下载。
