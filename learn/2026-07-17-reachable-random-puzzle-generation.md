# 可达随机题面：先生成材料，再从材料派生目标

适用于算术靶题、词语拼接、配方组合、卡牌凑值等“每局随机材料 + 一个公开目标”的本地小游戏。

## 随机目标不等于有效题面

如果先在一个漂亮的数值区间内随机目标，再随机发材料，就可能得到完全无解的局。玩家无法区分“我没想到”与“系统根本没给解”，公平感会迅速消失。

更稳的顺序是：

1. 生成满足唯一性和数量约束的材料；
2. 枚举材料允许形成的表达式或组合；
3. 过滤产品允许的目标范围；
4. 去重后，从可达集合中安全随机选择目标；
5. 把材料与目标作为同一份不可变 round plan 交给状态机。

这保证“开局存在至少一条解”，但不保证多人草拟后某位玩家仍拿得到解。后者可以成为策略，而不是生成器缺陷。

## 把生成器和 reducer 分开

纯 reducer 不应自己读随机数。它只接受经过 `isValidRoundPlan` 校验的 plan；浏览器编排层负责 `crypto.getRandomValues`，测试则注入确定性 `randomIndex(maxExclusive)`。

分层带来三个好处：

- 所有规则分支都能用固定 plan 重放；
- 安全随机不可用时可以明确失败，不必偷偷退化到 `Math.random`；
- plan 能在进入 reducer 前完成深拷贝/冻结，调用方之后修改数组不会改变已开始的局。

## 有限索引要拒绝采样

均匀的 32 位整数直接 `% n` 只有在 `n` 整除 `2^32` 时才严格均匀。通用做法是计算最大可整除接受区间，尾部值返回 `null` 并重抽。生成器的洗牌、目标选择和先手硬币都复用同一个无偏索引契约。

## 多人抢牌需要区分两种承诺

- **题面可达**：开局市场中存在精确表达式；生成器可以证明。
- **个人可达**：轮流拿牌后某位玩家仍拥有精确表达式；公开草拟玩法通常不承诺。

README 和 UI 只应该说前者。把后者写成承诺，会与抢牌、阻断和先后手策略直接冲突。

## 验证方法

- 对大量确定性索引序列验证材料唯一、范围合法、目标可由两张不同材料精确构成；
- 测试非法索引、空可达集、畸形 plan 和调用方数组修改；
- 对两种 starter 穷举完整选牌顺序，证明每张共享牌只能消费一次；
- 浏览器实际跑普通胜、精确命中、等距平局、三局交替与重开；
- 静态扫描确保没有 `Math.random` 回退、网络与持久化 API。

反例是只在 UI 层“尽量挑一个看起来能算的目标”，或让 reducer 在测试中也自行随机。前者不能证明题面，后者不能稳定重放。
