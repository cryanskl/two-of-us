# Candle Wishes：本地直开与浏览器证据边界

日期：2026-07-25

## 结论

A 级作品的“本地双击可用”和“浏览器运行态交互通过”是两类不同证据，不能互相替代。

- 本地直开合同应由静态事实证明：入口是普通 `index.html`；资源全部使用相对路径；脚本按 `config.js → logic.js → app.js` 的经典脚本顺序加载；不存在 ES module、`fetch`、远程 URL、网络、存储、权限或服务端依赖。
- 浏览器运行态证据用于证明实际 DOM、焦点、键盘、触摸、响应式、动画降级、控制台和请求行为。
- 如果受控浏览器的 URL 策略拒绝 `file://`，应保留原始拒绝事实，不尝试绕过，也不能把 localhost 的 HTTP 运行结果写成已经验证文件协议。
- 如果另行获得 localhost 运行证据，它只能证明相同资源在本机静态服务下的 UI 行为；最终记录必须明确协议差异。

## 本次触发

Chrome 控制能力拒绝导航到 Candle Wishes 的 `file://` 入口，理由为浏览器 URL 安全策略。此前的实现合同和 Node 静态测试仍能证明它没有主动要求服务端，但不能声称受控 Chrome 已完成真实文件协议验收。

仓库全量测试第一次还因工作树没有 `node_modules` 而失败：共享运行时缺少锁定依赖 `qrcode@1.5.4`，并使三个启动复用集成测试超时。执行 `npm ci --ignore-scripts --no-audit --no-fund` 后，没有改动依赖清单或锁文件，全量测试恢复通过。这类环境缺失应与作品缺陷分开记录。

## 后续执行模板

1. 先检查并安装仓库锁定依赖。
2. 对 A 级入口先跑资源闭包和禁止 API 的静态合同。
3. 浏览器工具允许时再做真实 `file://`；若策略拒绝，立即记录并停止同结果绕行。
4. 单列“静态直开合同”“实际协议”“运行态 UI”三栏，禁止用一个绿色结果覆盖另一个未测项。
