# 密封流程的版本队列与可验证回合编号

## 1. 证明与状态是两条因果链

双端密封玩法通常同时存在：裁判发出的秘密结果、主机发出的公开状态。Socket.IO 能保持同一连接内的事件顺序，却不能把不同 socket、不同发送者产生的两条链合并成全局顺序。

因此“状态先到就暂存一条”只覆盖最简单的乱序。真实序列可能是：揭晓状态、下一题状态、裁判结果。客户端应把经过 envelope Gate 的未来状态放入有界队列，按 `version` 重放；每接受一个状态，就用新状态继续验证下一条。

队列不是绕过验证的快捷通道。房间、当前 host、消息类型、成员集合、单调版本和 reducer 推导仍必须逐条满足；无效消息只保留在边界内或丢弃，不能因为“排过队”就直接渲染。

## 2. 幂等 tombstone 要求客户端编号可证明

密封 registry 保留完成轮次是正确的：网络重试命中同一个 `roundId` 时只返回 `replayed`，避免重复揭晓。反例是客户端允许任意“不同于当前”的编号；它可能复用更早的完成轮，得到成功 ack 却收不到新结果。

若公开状态不准备保存完整的 `usedRoundIds`，可以让编号由已有状态确定性生成：

```text
roundId = f(quizId, questionIndex)
```

状态机可在不扩充 payload 的情况下验证当前编号；新局更换 `quizId`，同一题号也不会撞上旧 tombstone。这比依赖随机字符串“几乎不会重复”更适合协议测试和故障推理。

## 3. 验证矩阵

- 结果先到、状态后到；
- 状态先到、结果后到；
- 两个连续状态先到、结果最后到；
- 旧版本、重复版本、跳版本和伪造中间状态；
- 当前编号重复、历史编号复用、新局相同题号；
- 成员或 host 变化时同时清空证明、队列与私密选择。

只测前两种交换顺序，仍不足以证明密封状态机能在真实双端节奏下收敛。
