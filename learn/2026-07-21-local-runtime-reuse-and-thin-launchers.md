# 本地运行时复用：显式身份、确定 loopback 与薄启动器

## 适用范围

同一仓库里有多个必须经过本地 HTTP 服务启动的页面，希望每个项目都能双击直达，同时避免重复双击产生多个常驻服务。

## 稳定结论

### 1. 端口占用不等于服务身份

不能因为首选端口已有 HTTP 响应就直接复用。最低限度应同时核对专用 identity header、health 协议版本、候选端口与本机地址，并再次读取和验证目标目录。探测应短时、只读、拒绝重定向；任何不一致都按“不可信”处理，再走正常启动路径。

identity header 只用于区分普通本地服务，不是密码学认证。若威胁模型包含本机恶意进程，还需要随机 secret、进程间通道或操作系统级访问控制。

### 2. listener 与公告地址必须属于同一地址族

`localhost` 是名称，不保证解析为 `127.0.0.1` 还是 `::1`。当生产服务绑定 IPv4 `0.0.0.0` 时，本机公告和复用探测应明确使用 `127.0.0.1`；局域网入口再独立从真实 IPv4 网卡生成。

有价值的回归不是只检查字符串，而是在同一数值端口同时建立 IPv4 与 IPv6-only 服务，分别请求 `127.0.0.1` 和 `[::1]`，证明浏览器不会被名称解析带到另一服务。

### 3. 作品启动器应该保持“薄”

每个作品目录只保留平台入口，传递稳定的作品 ID 给根启动脚本。依赖、端口策略、身份探测、浏览器打开和退出信号都由共享运行时统一拥有。这样作品仍然可以“找到目录就双击”，又不会产生多套 `node_modules`、端口规则或修复分支。

### 4. 复用进程不能转移所有权

第二个启动器确认已有服务后，只负责打开目标并以成功状态退出。它不注册针对首进程的退出处理、不关闭既有 socket，也不创建后台守护进程；首个进程仍是唯一生命周期所有者。

## 反例

- 只调用 `/api/health`，不验证响应头、版本和 catalog；
- 允许 fetch 自动跟随重定向，再把跳转后的响应当作本机服务；
- listener 绑定 `0.0.0.0`，却公告 `localhost`；
- 每个作品复制一份安装和启动逻辑，导致依赖版本与 bug 修复漂移；
- 第二个启动器复用成功后仍保持事件循环或尝试管理首进程。

## 验证方法

1. 纯函数测试候选端口、65535 边界、timeout 与 timer 清理；
2. 用错误 header、错误 health、畸形 catalog、跨源入口和重定向证明 fail closed；
3. 真实 child process 启动两次，证明第二次退出、两次目标 URL 同端口、首进程仍存活；
4. 用无关 HTTP 服务占据首选端口，证明它不会被复用且新运行时选择下一端口；
5. 用 IPv6-only 同端口服务验证确定的 IPv4 loopback；
6. 停止首进程后重新监听该端口，证明资源已释放。
