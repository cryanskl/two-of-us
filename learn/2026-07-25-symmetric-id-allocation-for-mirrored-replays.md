# 镜像确定性不仅要求物理对称，也要求身份分配对称

## 适用场景

确定性 reducer 同时具备：

- 两个可交换的玩家、队伍或分区；
- 同 tick 原子创建多个实体；
- 实体 ID 进入状态、排序、事件或哈希；
- 镜像 / 置换日志应得到等价状态。

## 容易漏掉的测试

下面的性质很弱：

```text
mirror(mirror(state)) == state
```

它只证明镜像函数是 involution（自反两次恢复），不能证明模拟规则与镜像交换：

```text
mirror(reduce(state, action))
  == reduce(mirror(state), mirror(action))
```

如果同刻创建请求总按“左方、右方”遍历，并从一个全局计数器连续取 ID，物理位置
和 owner 可以完全对称，ID 仍会绑定到错误的镜像实体。只要 ID 进入规范状态或
哈希，两条重放就会分叉。

## 可复用方案

把实体 ID 看成规则的一部分，而不是调试附属物。对两个固定席位，可按创建批次
预留 ID 对：

```text
pairBase = 1, 3, 5, ...
leftId   = pairBase
rightId  = pairBase + 1
```

只要该 tick 至少成功创建一个实体，下一批基址就推进 2；未使用的席位 ID 留空。
镜像时翻转奇偶，历史 ID 无需因后续创建重新编号。这样同时满足：

- 不同 tick 的实际 ID 单调增加；
- 同 tick 的创建顺序不影响 ID；
- 单方创建和双方创建都能稳定镜像；
- 某个镜像伙伴后来销毁，也不丢失身份映射；
- state validator 可以用 ID 奇偶校验 owner。

## 不应采用的补丁

仅对“当前仍存活、年龄相同”的实体交换 ID 不够。若一对同时创建的实体中已有一
个销毁，当前 state 已无法从存活集合恢复原创建配对，镜像仍会分叉。

从哈希中删除 ID 也只是隐藏问题：事件关联、调试追踪和依赖 ID 的稳定排序仍可能
不一致。除非 ID 明确不是逻辑字段，否则应修复分配规则。

## 验收组合

至少同时验证：

1. 镜像函数二次调用恢复；
2. 单方创建日志的 reducer 镜像等价；
3. 双方同刻创建日志的 reducer 镜像等价；
4. 一方实体先销毁后的后续镜像等价；
5. 多组长日志的规范状态与哈希等价；
6. 非法 ID / owner 组合在 state 边界被拒绝。
