# C 级双设备作品的最小同步模式

## 1. 服务端只管成员与传输

共享运行时只维护房间成员、主机迁移和 `room:action` 广播，不理解“按住”或“解锁”。玩法规则留在作品自己的纯状态层，后续画猜、抢答和合作迷宫可以复用同一协议，而不必不断给服务器增加游戏专用事件。

## 2. 本地动作先落状态，再发送事件

玩家按下按钮时，当前页面先执行 `setMemberHold()`，再广播 `{ type: "hold", data: { active: true } }`。这让本地触控立即有反馈，网络只负责让另一端追上。远端动作使用发送者 socket ID 更新对应成员，不依赖容易冲突的昵称。

## 3. 成功事件仍要校验前置条件

收到远端 `unlock` 时不能直接相信消息；状态层只有在当前两位成员都处于按住状态时才接受。Socket.IO 保证同一连接内消息有序，但前置校验还能防止旧消息、错误调用或未来协议变更直接跳过玩法条件。

## 4. 成员变化清空瞬时状态

房间从一人变两人、有人断开或新成员替换时，所有 holds、计时起点和 unlocked 都归零。短暂的手势状态不能跨成员继承，否则新加入的人可能看到已经进行一半的机关。

## 5. 共享房间与双人上限分层

通用房间允许更多成员，但“同心解锁”只取最早两位作为玩家；第三位加入后由客户端主动离开。这样不需要为了一个作品把共享运行时的房间上限改死，同时前两位的状态也不会被第三人打断。
