# 可恢复的私人答案 Gate：不留输入，也不让对方卡住

适用范围：纪念日问答、私人暗号、线索解锁、逐段告白等“答案来自双方记忆，但体验必须温柔可完成”的本地网页惊喜。

## 核心结论

私人答案玩法同时有三个目标：答案判断可信、输入不被无意保留、忘记答案也能完成。三者不能靠 UI 文案保证，应分别落到权威逻辑、最小状态和确定性恢复路径。

```text
原始输入（瞬时）
→ 逻辑层规范化并比较配置答案
→ 只返回 wrong / correct / rescued
→ 状态只保存题号、错误次数和已解星位
→ UI 投影状态
```

不要让 UI 先算出 `correct = true` 再通知 reducer“答对了”。那会让任意按钮脚本绕过答案 Gate。生产动作应同时接收当前状态、原始输入和受控配置，并在纯逻辑内完成比较。

## 状态白名单比“记得别保存”可靠

只是不写 `state.answer = input` 很容易在调试时回退。更稳妥的方法是：

- 初始状态只有固定字段；
- 校验要求精确字段集合，多一个 `rawAnswer` 也视为畸形；
- 错误结果只保存 `{ clueId, type, wrongCount }`；
- 正确与帮助通过都只保存配置中的公开星位 ID；
- UI 不记录提交历史，刷新自然清空。

这样测试可以枚举状态键并搜索序列化结果，隐私边界由代码结构而不是开发纪律维持。

## 恢复路径必须与正确路径汇合

“无限重试”不等于可完成；私人记忆可能确实忘了。一个温和但可验证的策略是：前两次提供提示，第三次固定开放帮助动作。帮助动作应写入与正确答案完全相同的进度数据，只在结果类型上保留 `rescued` 以选择不同文案。

这会形成一个汇合点：

```text
正确答案 ───────────────┐
                        ├→ linked → 显式继续 → 下一题
第三次错误 → 帮助校准 ─┘
```

如果帮助路径发明第二套“临时解锁”字段，绘图、进度、继续按钮和最终 Gate 都要理解两种成功，分叉很快会漂移。

## 提示策略只拿最小上下文

让准备者写自定义提示很有价值，但策略函数不应收到答案数组、原始输入或完整状态。只传冻结的 `{ clueIndex, wrongCount }`，并限制返回文本长度；策略报错或返回空值时回退确定性默认文案。

第三次错误不要再调用自定义策略，否则准备者的一行错误代码可能把兜底入口取消。恢复能力应由产品规则拥有，而不是由文案扩展点拥有。

## 揭晓还需要第二个 Gate

全部答对只代表 `ready`，不等于最终正文已经出现。`ready` 可以创建线索汇总或星码词，但最终标题、正文、结尾和署名应在用户点击“揭晓”后才进入 DOM。重开必须销毁这些节点，而不是用 CSS 隐藏。

这使验收可以分开证明：

- 逻辑测试证明任意题都能经正确或帮助路径到达 `ready`；
- DOM 检查证明 `ready` 没有最终正文；
- 揭晓后正文存在；
- 重开后正文节点数量回到 0。

## 信任边界

本地、不联网、不保存不等于加密。答案放在 `config.js` 时，能读取源码的人就能看到它。README 应明确这是一段惊喜节奏，不是口令认证；不要用哈希或混淆制造虚假的安全感，除非产品真的需要并实现了威胁模型。
