# 热座秘密的公开投影与重复元素反馈

## 适用范围

适用于两个人共用一台设备、需要交接隐藏信息的本地互动：猜码、出题与答题、轮流布阵、秘密选择、记忆挑战和逐步揭晓。文中的多重集合反馈适用于序列中允许重复元素、但只公开“位置正确”和“元素存在但位置不对”数量的玩法。

它不适合把同一设备上的对手视为恶意攻击者。JavaScript 进程内存、源文件和开发者工具都不是密码学安全边界；如果需要抵抗主动检查，应改用双设备、本机裁判或真正的提交—揭晓协议。

## 关键结论

### 1. 权威状态可以知道秘密，公开 view 不应该知道

将系统分成三层：

```text
权威状态（含当前秘密）
        ↓ 按 phase 投影
公开 view（只含当前阶段可见字段）
        ↓ 结构化渲染
阶段 DOM（只创建公开节点）
```

权威 reducer 需要秘密才能裁决猜测，但 UI 不应直接接收整份 state。公开投影函数应按阶段返回不同形状：

- 设置且未遮盖：可以返回当前设置草稿；
- 设置且已遮盖：草稿字段为空，只有“恢复设置”能力；
- 交接与猜测：不返回秘密、秘密草稿或可逆编码；
- 本轮结果：此时才返回本轮秘密；
- 总结果：只返回已经公开的两轮摘要。

这样，即使某个组件作者忘了隐藏元素，也没有数据可以误渲染。

### 2. 隐藏旧节点不等于删除秘密

以下做法都会把秘密留在 DOM：

- 给设置面板加 `hidden`；
- 切换 `display: none`；
- 把文字改成圆点但保留 `data-*`；
- 复用节点，只替换视觉图标；
- 用 `aria-hidden` 认为读屏和页面搜索就不会发现。

阶段切换应以公开 view 为输入，对阶段根节点执行结构替换，例如 `replaceChildren()`，再从零创建下一阶段。测试不仅要查询“看不见”，还要断言秘密名称、ID、序列和 `data-*` 在整棵当前 DOM 中不存在。

### 3. 生命周期自动遮盖必须显式适配事件参数

`blur` 和 `visibilitychange` 是隐私辅助，而不是业务 action。监听器应该显式把 DOM 事件转换为业务枚举：

```js
window.addEventListener("blur", () => cover("blur"));
document.addEventListener("visibilitychange", () => {
  if (document.hidden) cover("hidden");
});
```

不要直接传 `addEventListener("blur", cover)`；浏览器传入的是 `FocusEvent`，严格 reducer 应拒绝事件对象。也不要在恢复焦点或页面重新可见时自动揭开秘密，因为设备可能已经交给另一位玩家。

### 4. 反馈必须先同位，再消费剩余频数

假设秘密与猜测长度相同，且都允许重复。正确算法分两遍：

1. 第一遍比较同一索引；相等就计入 `exact`，不相等的秘密元素进入剩余频数表，不相等的猜测元素进入待匹配列表。
2. 第二遍扫描待匹配猜测；只有剩余频数大于 0 才计入 `misplaced`，并立刻减 1。

```text
secret = A A B C
guess  = A B A A

同位：第 1 格 A，exact = 1
剩余秘密频数：A×1, B×1, C×1
剩余猜测：B, A, A
消费后：B 与 A 各命中一次，最后一个 A 无剩余
结果：exact = 1, misplaced = 2
```

若对每个猜测元素独立执行 `secret.includes(value)`，三个剩余元素都会被认为存在，错误得到 `misplaced = 3`。

### 5. 反馈应是数量与语义，不依赖颜色

公开结果至少包含可读文字和数字，例如“同位 1 / 有料 2”。圆点、方钉、颜色、震动或动画都只是投影，不能是唯一信息来源。强制颜色、无动画和读屏环境仍应能理解结果。

若参考商业猜码机制，应避免沿用商标名称、红白提示钉、黑色塑料板和包装式布局；机制可研究，具体表达与 trade dress 仍需重新设计，并在借鉴声明中写清边界。

### 6. 公共 action 与公开 view 应共同做秘密边界测试

仅测试 `scoreGuess()` 不足以证明热座安全。推荐至少覆盖：

- 设置草稿满格、重复上限与最少不同元素；
- 自动遮盖、手动遮盖、恢复与错误阶段动作；
- covered、handoff、guessing view 不含秘密字段；
- DOM 不含秘密名称、ID、序列或配料节点；
- 本轮结果只揭晓本轮秘密，推进后历史只保留已公开摘要；
- 重开清空两轮秘密、猜测和结语；
- 开发者工具边界在 README 中诚实说明。

### 7. 公开投影也让测试和前端更稳定

当视图只接触阶段所需字段时：

- 前端不会依赖 reducer 的内部数组身份；
- 序列化、重放和 DOM 测试能使用同一份公开合同；
- 改内部状态结构时，不必同步修改每个组件；
- 结果页无法意外读取下一轮尚未公开的内容；
- `replaceChildren()` 的整段替换可以自然恢复焦点到新阶段标题或主动作。

## 反例

- 把秘密写进 `data-secret` 再遮住设置面板：页面搜索与 DOM 检查仍能读取。
- UI 直接拿完整 state，再约定“不要渲染 secret”：这是团队约定，不是结构性边界。
- 窗口重新聚焦就自动恢复设置态：设备交接后会替另一位玩家揭开秘密。
- 用 `includes` 计算错位：重复猜测可以重复消费同一个秘密元素。
- 只显示红点和白点：强制颜色或色觉差异下无法理解。
- 在文档中写“本地加密”：同页 JavaScript 内存并没有加密或隔离进程。

## 验证清单

- 权威 state 与公开 view 是不同对象，公开数组不共享引用；
- 每个阶段的 view 字段白名单都有精确测试；
- covered / handoff / guessing 的 DOM 全局扫描不命中秘密；
- 失焦与隐藏显式传递字符串原因，重新可见不自动揭开；
- 全同位、全错位、零命中、交叉重复和多余重复均有表驱动用例；
- `exact + misplaced` 永远不超过序列长度；
- 反馈同时含数量、文字和非颜色形状；
- 结果揭晓、换轮、总结果与重开均有真实浏览器路径；
- README 明确“面对面遮挡，不是密码学加密”；
- 借鉴声明列出固定版本、许可证、权利主体、零复制与商业表达边界。

## 本仓库实例

“藏好这一味”使用四格秘密、六种配料、同种最多两份、整份至少三种、七次猜测和双轮换位。`getRecipeView()` 按阶段投影公开数据，前端用整段 DOM 替换删除秘密节点；`scoreGuess()` 先计算同位，再消费剩余配料频数。22 条逻辑测试覆盖重复元素、阶段投影、畸形 action、双轮计分、JSON 往返与 40-action 黄金重放。
