# 同时输入游戏：原子 tick、失败尝试与可重放裁决

适用范围：光轨、生存蛇、同时落子、双人竞速抢点、弹幕对撞等“多名玩家在同一时间片内可能争夺同一空间”的本地或联网游戏。

## 核心结论

“每 100ms 让两名玩家各走一步”听起来像同时，但如果代码按数组顺序逐个更新占用格，结果仍然是先后手：玩家 1 先写入格子，玩家 2 随后会把它当作旧障碍；交换数组顺序就可能交换胜负。

公平的 tick 必须是一个事务：

```text
同一旧快照
  → 汇总双方输入
  → 计算双方新方向
  → 计算双方尝试位置
  → 读取旧占用并收集所有碰撞原因
  → 检查玩家之间的同时冲突
  → 一次性裁决
  → 全安全才一起提交
```

任何一步在裁决完成前写回权威棋盘，都会把“同时”退化成“按循环顺序轮流”。

## 旧轨迹与本 tick 尝试要分层

碰撞检查至少分两类：

1. 对旧世界的碰撞：越界、自己的旧轨、对方的旧轨；
2. 本 tick 玩家之间的冲突：进入同一目标格、交换两个旧头部格。

第二类无法通过“检查 occupied”完整表达，因为两个目标在旧快照里都可能是空的。必须在拿到所有 `nextPosition` 后做成对比较。

同样地，fatal tick 应记录尝试位置与原因，但不能把安全一方的新格单独写入轨迹。如果 P1 撞墙、P2 安全，先提交 P2 再结束会造成一个没有对应完整 tick 的半状态；重放和碰撞画面会因此不一致。

## 多原因不是多次结算

一个玩家可能同时拥有多个死亡原因。例如两人进入同一个已经被占用的格：

```text
P1: rival-trail + same-destination
P2: own-trail   + same-destination
```

原因集合应该完整保留，方便解释和调试；但该 tick 只能产生一个 outcome。固定原因排序还能让快照和回归测试稳定：

```text
wall
→ own-trail
→ rival-trail
→ same-destination
→ head-swap
```

胜负只看两人的原因集合是否为空：

- 一方为空、另一方非空：空的一方获胜；
- 双方都非空：平局；
- 双方都为空：一起提交并继续。

不要用“死亡原因优先级”给同时死亡强行分胜负，也不要用玩家编号打破平局。

## 输入事件不是逻辑顺序

浏览器可能先收到玩家 2 的 `pointerdown`，再收到玩家 1 的 `keydown`。事件到达先后只应该更新当前 tick 的两个槽位：

```js
pendingTurns = [0, 0];

function queueTurn(player, turn) {
  pendingTurns[player] = turn;
}
```

tick 开始时复制 `[p1, p2]` 并立即清零，然后把这一对作为不可拆分输入交给 reducer。同一玩家在 tick 前多次改变主意时，可以冻结“最后一个有效意图为准”的规则；两位玩家之间则不存在先后。

需要测试两种顺序：

```text
P1 左 → P2 右
P2 右 → P1 左
```

它们必须产生逐字段相同的下一状态。

## 输入日志可以取代可变占用数组

小型短局游戏可以把权威状态定义为出生变体与 tick 日志：

```js
{
  spawnVariant: 0,
  ticks: [
    { turns: [-1, 1] },
    { turns: [0, 0] }
  ]
}
```

占用格、头部位置、方向和 outcome 全部通过 `replayRound()` 派生。它的优势是：

- bug 复现材料很小；
- Canvas 和 UI 无法持有第二份权威真相；
- 同一日志天然可做确定性回归；
- 公共状态无需暴露可变 `Uint8Array`、`Set` 或 `Map`；
- round 数量有上限时，重放成本也有明确上限。

若地图很大或对局极长，可定期保存不可变 checkpoint，再重放 checkpoint 后的日志；不要因此让渲染缓存成为权威状态。

## rAF 只负责消费时间

同时裁决解决的是“一个 tick 内谁先”，固定步解决的是“不同刷新率推进多少 tick”。两者缺一不可：

- reducer 每次只推进一个整数 tick；
- rAF accumulator 决定本帧消费几个 tick；
- 单帧追赶设上限；
- 页面隐藏、失焦或间隔过长时暂停并清 accumulator；
- 恢复后从新帧重新累计，不补跑后台时间。

后台补跑尤其危险：两名玩家回来时已经经历几十个没有输入的 tick，即使技术上确定性，也不符合实际双人玩法。

## 最小测试矩阵

至少固定以下向量：

1. 双方安全，两个格一起提交；
2. 单方越界，另一方获胜；
3. 双方越界，平局；
4. 自己旧轨与对方旧轨；
5. 进入同一空格；
6. 交换头部位置；
7. 两人以不同原因同 tick 死亡；
8. 同一玩家同 tick 多次输入；
9. 两位玩家输入事件顺序互换；
10. 玩家编号、出生点和轨迹镜像后，结果也镜像；
11. fatal tick 不出现半提交；
12. 同一日志重放两次完全相同；
13. 结束后继续 step 返回原引用；
14. resize、DPR、reduced motion 和 rAF 分片不改变状态。

## 浏览器验证补充

纯逻辑通过并不等于输入层已经公平。浏览器还要验证：

- 两个不同 `pointerId` 能在同一 tick 写入两名玩家槽位；
- 键盘游戏键才阻止默认行为；
- `keydown.repeat` 不生成额外转向；
- Pointer 与键盘进入同一个 `queueTurn()`；
- 触控按钮 `touch-action: none`，棋盘不吞页面手势；
- 48px / 56px 目标在窄屏没有重叠；
- console、page error 和外部请求为 0。
