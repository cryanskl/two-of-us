# 非对称同屏合作：让规则 Gate 证明双方都不可替代

## 适用范围

适用于两个人在同一屏幕操作不同职责的轻量网页游戏，例如领航与驾驶、侦察与移动、开门与搬运。它解决的是“合作是否由规则保证”，不是秘密信息隔离。

## 关键结论

### 1. 同屏角色分工不等于秘密状态安全

同一页面上的 DOM、Canvas 与 JavaScript 都由同一台设备持有。视觉上把信息放在左右两区，不能阻止另一位玩家看到或检查。因此文案应诚实地称为“角色分工”，不应宣称密码学意义的隐藏或防窥。

### 2. 每个输入通道只改变自己的权威状态

灯塔输入只更新 `angle / angularVelocity`，船舵输入只更新 `position / velocity / heading / rudder`。渲染层从这两组状态投影光束和船体，不反向写规则。这样可以用测试直接证明：

- 中性灯塔输入无法发现全部航标或点亮港口；
- 中性小船输入无法进入检查点或靠港；
- 任意一方都不能通过操纵另一通道的视觉效果伪造完成。

### 3. 完成条件要同时引用双方的当前状态

“先由 A 解锁，再由 B 单独完成”仍可能退化成轮流单人操作。更强的合作 Gate 应在最终时刻同时要求双方维持条件。例如“为你引航”同时检查：必要航标已发现、港口当前受光、船在泊位内、速度足够低、航向正确，并连续保持 `0.6s`。

### 4. 可玩性证明应复用生产 reducer

确定性测试不应另写简化物理。把规划好的双人输入逐步送入同一个 `stepGame()`，既证明关卡可解，也验证碰撞、检查点和最终 Gate 没有被测试替身绕过。再分别把一方输入归零，验证双方必要性。

## 反例

- Canvas 自己计算“港口看起来被照亮”，但规则只检查船的位置；
- 灯塔按键直接修改船的速度以提供辅助；
- 只测试一个手工拼出的完成状态，没有走生产状态转换；
- 把同屏左右分栏描述成“对方绝对看不到”。

## 验证清单

- 两组输入是否写入互不重叠的权威字段；
- 最终 Gate 是否同时依赖双方当前状态；
- 是否存在至少一段需要同一步联合输入的路线；
- 中性任一方是否都无法完成；
- Canvas/DOM 是否只消费派生状态；
- 隐私文案是否没有超出同屏技术边界。
