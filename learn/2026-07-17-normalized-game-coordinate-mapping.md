# 规范化游戏坐标与 CSS 布局坐标只保留一个来源

实时小游戏常把规则状态保存成 `[-1, 1]`，再映射到响应式 DOM 的百分比位置。危险不在公式本身，而在终点、角色和辅助线分别维护“看起来差不多”的常量。

## 1. 规则值与布局值分层

规则层只认规范化坐标：

```text
position ∈ [-1, 1]
```

布局层只定义一次最大旅行范围：

```text
travel = 38%
visualPosition = 50% + position × travel
```

角色位置、左右终点、meter 的可访问文本和截图断言都从这两个值推导。不要让 CSS 再写一个“接近终点”的 8.4%，也不要从计算后的像素反推规则胜负。

## 2. 响应式不改变语义

百分比旅行范围会随容器缩放，因此 1269px、390px 和 320px 的终点像素不同，但 `position = ±1` 始终落在对应针位。规则阈值不需要知道 viewport，也不应读取 `getBoundingClientRect()`。

## 3. 验收要对齐事件而非只看美观

截图时同时检查：

- 状态机已经进入胜局；
- meter 的 `aria-valuenow` 为 `-100` 或 `100`；
- 织带结中心与对应终点针的中心差在像素容差内。

只确认“结移动了”和“页面显示胜利”仍可能漏掉两套坐标漂移。视觉反馈承载规则语义时，它也需要可以量化的回归断言。
