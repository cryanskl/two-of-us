# 有限库存精确覆盖：后缀可解性、原子前缀与独立穷举 Oracle

## 适用范围

适用于“若干参与者各自拥有有限资源，逐轮组合资源满足公开需求，并要求最终恰好用完”的本地小游戏或流程题，例如共同照料、配方拼装、行程装箱、有限行动点分配。资源类型少、轮数有限时尤其合适。

不适用于资源可无限补充、目标允许任意剩余、或状态空间大到无法穷举且没有可靠剪枝的系统。

## 关键结论

### 1. 当轮匹配不等于全局可完成

假设第 `d` 轮需求是无序对 `R[d]`，两席剩余库存为 `I[d]`，本轮选择有序对 `(a, b)`。至少要依次检查：

1. A 的 `a` 与 B 的 `b` 都还有库存；
2. `sort(a, b) === sort(R[d])`；
3. 扣减后，从 `d + 1` 到终局至少存在一条把所有库存恰好耗尽的路线。

第 2 条只证明眼前配对正确。若缺少第 3 条，玩家可能用对了今天的工具，却把某一席未来唯一需要的工具提前耗掉，几轮后才发现死局。

因此 evaluator 应返回有区别的结果：

- `pair-mismatch`：本轮需求就不匹配；
- `future-stranded`：本轮匹配，但扣减后的后缀解数为 0；
- `accepted`：本轮匹配，且后缀解数至少为 1。

失败原因分开后，界面能给出诚实反馈，测试也能分别构造邻接负样本。

### 2. 用后缀计数器统一“能不能继续”和“解是否唯一”

有限状态下可定义：

```text
countSuffix(day, inventories):
  if day == end:
    return inventories 全为 0 ? 1 : 0

  total = 0
  for A 的每种可用资源 a:
    for B 的每种可用资源 b:
      if (a, b) 匹配当天需求:
        total += countSuffix(day + 1, 扣减后的库存)
  return total
```

用 `day + 两席三类库存` 作为 memo key，可把重复后缀合并。返回“解的数量”比只返回布尔值更有用：

- `0`：当前前缀会困死；
- `>= 1`：可安全提交；
- 初态为 `1`：题面拥有唯一完整路线，可作为设计 Gate；
- 初态大于 `1`：仍可玩，但不应在文档中宣称唯一解。

计数属于规则层内部证据，不应自动暴露给 public view。公开完整解数、推荐下一步或唯一路线，会把合作规划退化成照抄答案。

### 3. accepted 必须原子提交，失败不能留下半扣库存

成功动作应一次产生完整的新状态：

```text
next = {
  inventories: deductedInventories,
  completedDays: [...completedDays, committedDay],
  phase: "day-result"
}
```

不要先扣 A、等待 B、再视结果回滚；也不要进入结果页后才追加完成记录。前者制造半提交与异常恢复问题，后者让结果页显示的“已经完成”与权威状态矛盾。

失败则保留原库存与完成前缀，只更新可丢弃的尝试次数或反馈阶段。这样“重试当前轮”天然成立，不需要补偿事务。

### 4. 结果页是一种已提交但未推进日序的合法状态

若 `dayIndex` 表示当前正在展示的日，而成功后先展示当日结果、再由 `NEXT_DAY` 推进，则不变量必须按阶段拆开：

- 普通选择/失败阶段：`completed.length === dayIndex`；
- 当日结果阶段：`completed.length === dayIndex + 1`；
- 完成阶段：全部轮次已提交，`dayIndex` 仍指向最后一轮。

试图用一个 `completed.length === dayIndex` 覆盖所有阶段，会把每个成功结果页都误判成非法状态。阶段不是装饰字段，它参与状态合法性定义。

### 5. Oracle 必须与生产求解器实现独立

仅用生产 `countSuffix` 生成期望值，再断言生产函数等于该期望，没有交叉验证价值。测试 Oracle 应采用独立代码路径：

- 直接写出资源字面量和当天需求；
- 不调用生产 `pairKey`、`countSuffix` 或 evaluator；
- 用不同的数据复制与遍历写法；
- 枚举全部合法库存总数状态，而非只测初态路线。

在“把七天，养成一朵花”中，独立 Oracle 覆盖了 2,892 个两席库存状态，并逐日核对九种有序选择；初态完整路线数为 1。它能发现 memo key、无序配对、终局剩余库存和扣减席位任一处的实现错误。

## 反例

- 只检查当天 pair：局部正确但未来困死。
- 成功后立即推进日序再渲染结果：结果页无法稳定知道刚完成的是哪一天。
- 失败先扣再补：任何异常分支都可能漏补一席。
- 把 `suffixSolutions` 放进公开 view：无意泄露题面可解性甚至唯一路线。
- 测试复用生产排序与递归：同一个 bug 会让实现和期望一起错。
- 只验证官方唯一路线：无法证明其他库存状态下求解器仍正确。

## 验证清单

- [ ] 初态后缀解数符合设计目标，若宣称唯一则必须等于 1
- [ ] 每轮所有有序资源组合都与独立 Oracle 一致
- [ ] 所有可枚举库存状态都经过独立交叉验证
- [ ] `pair-mismatch` 与 `future-stranded` 都保留库存和已完成前缀
- [ ] accepted 同时扣减两席库存并追加一条完成记录
- [ ] 第一轮与最后一轮结果页均满足阶段化前缀不变量
- [ ] 完整 action log 可重放，最终所有库存恰好为 0
- [ ] public view 不包含后缀解数、答案路线或内部 memo
