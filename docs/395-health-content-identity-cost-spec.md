# /api/health 的内容身份代价规格

- 状态：`implemented`
- 日期：2026-07-28
- 影响范围：`shared/runtime/server.js`、`scripts/runtime-reuse.mjs`、`shared/runtime/README.md`

## 问题

`/api/health` 在回答之前会 `await` 一次完整的内容身份重算：读遍 `index.html`、`package.json`、`experiences/catalog.json`、`shared/`、`capabilities/`、全部已安装作品目录和固定 vendor 资产，再逐字节哈希。当前实测约 **2.0 秒**，并随作品和素材继续增长。

代价落在了两类完全不同的调用者身上：

| 调用者 | 是否需要 `contentIdentity` | 实际付出 |
| --- | --- | --- |
| 门户（每次加载） | **否**，只用 `networkUrls`、`joinUrl`、`node`、`qrDataUrl` | 每次加载等约 2 秒才显示运行时状态与二维码 |
| 启动器的复用探测 | 是，这是它唯一的判断依据 | 约 2 秒，合理 |

也就是说，门户每次打开都为一个它根本不读的字段等待两秒，而且这个等待只会越来越长。这同时是 [`bugs/`](../bugs/) 中「复用探测超时」一类问题的上游成因：探测预算必须跟着这个数字一起抬。

## 决策：把重算变成显式索取，而不是默认行为

```text
GET /api/health                              → 立即返回，不含 contentIdentity
GET /api/health?verify=content-identity      → 重算并返回 contentIdentity
```

- 门户走第一条路径，不触发任何全仓读取；
- 启动器的复用探测走第二条，语义与改动前**完全一致**：与启动时一致则返回该身份，签出已变化或读取失败则返回 `null`；
- 未知或拼错的查询值（`verify=1`、`verify=`、`other=...`）一律走便宜路径，避免随手拼出来的 URL 拖慢运行时。

### 为什么是「省略」而不是「给一个未校验的值」

便宜路径本可以返回启动时算出的身份。但那个值只能证明「启动那一刻是这样」，不能证明「现在还是这样」——而复用判定要的恰恰是后者。如果把它放进同一个字段，任何调用者都无法区分手上的身份是否经过校验，安全边界会在无声中变松。

因此便宜路径**不返回这个字段**。对复用判定来说，「没有身份」和「身份不匹配」结论相同（不可复用），但前者不会让人误读。

### 兼容性

- 新启动器 ↔ 旧运行时：旧运行时忽略未知查询，照常返回 `contentIdentity`，复用仍然成立；
- 旧启动器 ↔ 新运行时：旧启动器不带查询，拿不到字段，于是判定为不可复用，另起一个运行时并占用下一个端口。这是安全的降级，而不是错误——何况这种组合意味着两份不同的签出，本来就几乎必然身份不同、不该复用。

## 结果

| 路径 | 改动前 | 改动后 |
| --- | ---: | ---: |
| `GET /api/health`（门户） | ~2.03 s | **~0.0015 s** |
| `GET /api/health?verify=content-identity`（探测） | ~2.03 s | ~2.04 s |

门户内实测：三个 API 请求都在页面开始加载后约 52 ms 发出，分别在 5 / 9 / 18 ms 内完成，运行时横幅与二维码几乎立刻就绪。

## 验收

- [x] 新增回归测试：连续三次普通 health 不触发任何一次 `contentIdentityProvider` 调用；四种错误查询值同样不触发；带正确查询时恰好触发一次；
- [x] 漂移检测行为不变：签出变化后带查询的 health 返回 `contentIdentity: null`，进程继续存活；
- [x] `start-reuse` 集成测试全部通过，顺序第二个启动器仍然复用第一个进程并让出下一个端口；
- [x] `npm test` 与 `npm run verify` 全绿。

## 未决

- 探测路径本身仍是约 2 秒，且随仓库增长。若将来需要压缩它，可选方向是先用 mtime/size 做廉价预筛、只在预筛变化时才做全量哈希——但那会把「内容相同」放宽成「元数据相同」，属于安全边界的改动，应单独评估，不在本次范围内。
