# C 级“连心四子棋”规格

## 1. Brainstorm 结论

首个 C 级双设备对抗作品采用 7×6 四子连线。它用完整棋盘状态验证双端轮流操作、主机权威判定、胜负同步和再来一局，同时避开实时网络延迟与隐藏信息的额外复杂度。

| 方案 | 双设备价值 | 复杂度与风险 | 本批决定 |
| --- | --- | --- | --- |
| 双设备反应力 | 两人同时抢按，气氛直接 | 网络延迟和客户端时钟会影响公平；与现有 A 级反应力对决重复 | 不采用 |
| 双设备拔河 | 同时操作，互动强 | 高频消息、节流和掉线公平性需要先建立更完整实时同步 | 后续 |
| 秘密出招 / 海战棋 | 双屏天然保护秘密 | 需要定向状态、提交/揭晓或较重棋盘流程 | 后续 |
| 四子连线 | 各看一屏、轮流落子，状态清楚 | 只需确定性棋盘与顺序消息 | 采用 |

作品名为“连心四子棋”。首批只做标准规则，不增加 AI、道具、计时、排行榜、账号、聊天、观战、棋盘尺寸选择或公网匹配。

## 2. 用户流程

1. 一台设备运行根目录 `npm start`，从门户打开“连心四子棋”；
2. 第一位创建五位码房间，第二位在同一局域网打开页面并输入房间码；
3. 两人到齐后，主机点击“开始对局”；
4. 当前玩家点击一列，棋子落到该列最低空位；
5. 双方轮流落子，先横、竖或斜向连成四颗同色棋子者获胜；
6. 棋盘填满且无人获胜则平局；
7. 对局结束后主机可点击“再来一局”，下一局交换先手；
8. 成员变化、主机迁移或连接断开时清空当前对局，重新等两个人开始，不做断线续局。

## 3. 游戏状态与纯逻辑

`logic.js` 不访问 DOM 或 Socket.IO，维护可测试的权威状态：

```text
schemaVersion, version, phase,
memberIds, board, currentPlayerId,
winnerId, winningCells, moveCount,
matchNumber, starterIndex
```

- 棋盘固定 7 列 × 6 行，以长度 42 的数组保存；空位为 `null`，棋子使用成员 ID；
- 阶段使用 `waiting / playing / finished`；房间人数是否 ready 由页面根据成员状态展示，不写入棋盘状态；
- `startMatch` 只接受两个不同成员；首局由成员列表第一位先手，再来一局切换 `starterIndex`；
- `applyMove` 只接受当前玩家、0–6 的整数列和未满列；合法落子填入最低空位并增加版本；
- 每次合法落子后检查横、竖、两条斜线；胜利时保存四个获胜格索引，棋盘满则结束为平局；
- 非法、过期或重复操作返回原状态对象，便于调用方可靠判断是否需要广播；
- `acceptPublicState` 只接受结构合法、版本严格递增且成员集合匹配的完整状态。

纯逻辑测试至少覆盖：

- 棋子落在列的最低空位；
- 非当前玩家、越界列和已满列被拒绝；
- 横向、纵向、两种斜向胜利；
- 棋盘填满时平局；
- 胜负产生后不能继续落子；
- 远端旧版本、畸形棋盘和成员不匹配状态被拒绝；
- 再来一局清空棋盘并交换先手。

## 4. 主机权威协议

复用共享 Socket.IO 房间协议，不修改共享服务器，不增加第三方依赖。

| 消息 | 方向 | 数据 | 约束 |
| --- | --- | --- | --- |
| `connect-four:move` | 非主机经 `room:direct` 发给主机 | `column, version` | 共享层验证发送者与目标均在房间；主机再验证回合与版本 |
| `connect-four:state` | 主机经 `room:action` 广播 | 完整公开状态 | 客户端只接受已知主机发送且版本递增的状态 |

主机自己的落子直接进入本地权威 reducer，再广播结果。非主机不能广播有效状态；主机不能替不在当前回合的成员落子。棋盘没有秘密信息，因此无需新增定向答案协议。

成员列表只取最早进入的两人；第三人加入时沿用现有 C 级作品的退出与提示流程。成员 ID 或主机 ID 变化立即重置对局，以免新成员继承旧席位。

## 5. 页面与输入

- 桌面和手机使用同一响应式 7 列棋盘；每列顶部或整列使用原生 `<button>` 作为落子入口；
- 非本人回合、等待开始、列已满或对局结束时禁止对应按钮；
- 状态区同时写清“你的颜色”“当前轮到谁”“胜负/平局”，不能只依赖颜色；
- 获胜四格有视觉标记，并通过 `aria-live="polite"` 宣布结果；
- 两种棋子使用颜色、符号和可访问名称共同区分；
- 390×844 下不横向溢出，触控目标不小于棋盘列可用宽度；
- `prefers-reduced-motion` 下取消落子位移动画；不播放声音、不震动、不请求设备权限。

## 6. 启动、依赖与隐私

- 等级：C，本地服务 + 局域网双设备；
- 安装：与仓库统一使用根目录 `npm install`；本作品不增加新依赖；
- 启动：根目录 `npm start` 或跨平台启动器；页面由本地运行时提供；
- 运行数据：房间成员、棋盘和胜负仅保存在两端内存及本机 Socket.IO 消息中；
- 公网依赖：无；不使用 CDN、远程字体、统计、账号、云数据库或公共 WebSocket；
- 房间仅面向可信局域网，不承诺公网暴露安全性。

## 8. 借鉴与来源声明边界

- 传统四子连线：采用“轮流向列中落子，率先横/竖/斜连成四子获胜”的通用棋类规则，不复制任何商业品牌的名称、视觉、棋子或素材；
- [bryanbraun/connect-four](https://github.com/bryanbraun/connect-four)（MIT）：调研阶段用于确认原生 Web 四子棋的交互与移动端可行性；不复制、改写或打包其源码、样式、音效和素材；
- [kbennett2000/lan-games](https://github.com/kbennett2000/lan-games)（MIT）：调研阶段用于比较局域网棋类的房间架构；不复制其服务器、数据库、房间页面或游戏代码；
- [Socket.IO](https://github.com/socketio/socket.io)（MIT）：本仓库共享运行时的直接依赖，本作品复用仓库现有安装与房间封装；
- 本仓库“隔屏画猜”：复用主机权威、版本门控、第三人退出和成员变化重置的内部经验，棋盘 reducer、页面与协议类型重新实现。

以上三个上游仓库的许可证已于 2026-07-15 通过 GitHub 当前 `LICENSE` 文件复核。作品 README 必须保留实际调研和直接依赖声明，不得只写“独立实现”。

## 9. 验收标准

- 两个 Chrome 标签页可创建/加入同一房间并开始对局；
- 双端棋盘、当前回合、落子、获胜四格和平局状态一致；
- 非当前玩家、满列、越界、旧版本和伪造非主机状态不会改变权威棋盘；
- 横、竖、两条斜线胜利及平局由自动测试覆盖；
- 再来一局清空棋盘并交换先手；
- 第三人被退出，成员或主机变化后不会继承旧对局；
- 390×844 无横向溢出，触屏和键盘都可完成一局；
- Chrome 控制台无 warning/error，Network 无公网请求；
- `npm test`、`npm run verify` 与 `git diff --check` 通过；
- README 包含完整“借鉴与来源声明”。
