# A 级“这一场雨，我们一起接”定向调研

调研日期：2026-07-20

对应创意：`C13 云朵配方`

建议目录：`experiences/co-op/cloud-recipe/`

建议等级：A（同屏双人、`file://` 直开、无第三方运行依赖）

## 1. 调研结论

这个题目值得实现，但不应做成又一个自由移动、托举或绳索物理游戏。仓库已经有“稳稳地，和你一起向前”和“一起，把家搬进来”，继续让两个人共同推一个物体，会在操作语义和合作证明上高度重复。

本作最清晰、最独特的核心应是 **可变区间接雨**：

- 舞台固定为 7 条雨道；
- 左席只控制云朵接雨区间的左边缘，右席只控制右边缘；
- 每一波有两颗同色配方雨滴，分别落在唯一正确区间的两端；
- 正确区间外紧邻灰滴；区间太窄会漏掉配方，太宽会接到灰滴；
- 两位玩家必须各自移动自己的边缘，才能把云朵调成唯一正确宽度；
- 三份配方、每份三波，全部采用固定脚本，失败只重试当前原料，没有生命、排名和惩罚。

它保留了“接住彩色雨滴、避开灰滴”的直觉，同时把合作从视觉装饰变成可以穷举验证的权限结构。

## 2. Brainstorm：三个方向与取舍

### 方向 A：双端自由物理云

两人分别拖动云朵两端，云会旋转、弯曲或惯性漂移。这种形态第一眼生动，但会重复仓库既有的双人托举、双端移动和稳定性玩法；触摸、键盘和帧率之间也更难保证完全一致。

**结论：不采用。**

### 方向 B：随机落物接取

彩滴和灰滴随机出现，两人共同移动一个篮子或云朵，以分数决定表现。这种规则容易理解，但随机序列会削弱复盘、测试和公平性；“共同移动”也不能证明两个角色缺一不可。

**结论：不采用。**

### 方向 C：固定配方的唯一接雨区间

每一波预先声明目标左端、目标右端和颜色。两端之外布置灰滴，使所有合法区间中只有一个能同时“接齐彩滴且不接灰滴”。两席权限互斥，结果可由纯函数重放。

**结论：采用，进入规格冻结。**

## 3. 机制草案

### 3.1 舞台与权限

- 雨道编号固定为 `0…6`；
- 当前云朵区间为闭区间 `[leftLane, rightLane]`；
- 永远保持 `0 <= leftLane <= rightLane <= 6`；
- 左席用 `A / D` 或左侧触控按钮，只能改变 `leftLane`；
- 右席用 `← / →` 或右侧触控按钮，只能改变 `rightLane`；
- 两端不得越过；越界输入是确定性的 no-op；
- 每波开始和失败重试都回到中性区间 `[2, 4]`。

### 3.2 一波雨如何判定

一波包含两颗同色目标雨滴，分别位于 `targetLeft` 与 `targetRight`。若目标区间左侧或右侧仍有雨道，则在紧邻位置各放一颗灰滴。

雨滴经过固定整数 tick 到达云朵时，一次性结算：

- 两颗目标滴都在当前区间内，且没有灰滴在区间内：成功；
- 接到任意灰滴：`contamination`，提示“云朵盛得太满”；
- 否则：`missed`，提示“还差一边没有接住”；
- 失败不改变配方进度，只增加当前波的尝试次数并重新开始。

### 3.3 固定配方候选

三份配方均使用蓝、金、玫瑰三色，但顺序不同；九个目标区间都与中性区间 `[2, 4]` 的左右端同时不同，避免某一席在某波完全不用操作。

| 配方 | 原料顺序 | 三波目标区间 |
| --- | --- | --- |
| 晨光露 | 蓝 → 金 → 玫瑰 | `[1,3]`、`[3,5]`、`[0,2]` |
| 晚霞糖露 | 玫瑰 → 蓝 → 金 | `[4,6]`、`[1,2]`、`[3,6]` |
| 星夜汽水 | 金 → 玫瑰 → 蓝 | `[0,1]`、`[1,5]`、`[5,6]` |

正式规格需要冻结每波 tick 数、阶段枚举、事件名和公开视图结构。

## 4. 合作必要性的可证明性

7 条雨道共有 `7 × 8 / 2 = 28` 个合法闭区间。对任一目标 `[L, R]`：

1. 任意严格子区间都会漏掉 `L` 或 `R` 上至少一颗目标滴；
2. 任意向左扩张的区间会接到 `L - 1` 的灰滴（若该雨道存在）；
3. 任意向右扩张的区间会接到 `R + 1` 的灰滴（若该雨道存在）；
4. 目标贴边时，不存在的外侧灰滴也不会制造第二个合法超区间，因为边界已不能继续扩张；
5. 所以 28 个合法区间中，只有 `[L, R]` 成功。

同时，九波的 `L` 与 `R` 都不同于默认值 `2` 与 `4`。若固定任一席不动，整局必然无法完成。这比“画面上两个人都在动”提供了更强的合作 Gate。

## 5. 本地实现可行性

### 5.1 运行等级

- 纯 HTML、CSS 与经典脚本；
- 不使用 ES Module、`fetch()`、服务端、数据库、localStorage、音频或网络；
- 所有文案、配方、规则和图片放在作品目录内；
- 双击 `index.html` 即可进入，因此属于 A 级。

### 5.2 确定性架构

- 规则层采用纯 reducer；
- 时间只以整数 tick 进入 reducer；
- `requestAnimationFrame` 仅负责把真实时间累积为固定 tick，不直接决定物理结果；
- 每波位置由 `waveTick / waveDurationTicks` 映射到 CSS 自定义属性；
- 同一初始状态和事件序列必须得到完全相同的结果；
- 应能穷举 28 个合法区间，验证每波恰好一个成功解。

### 5.3 可访问与生命周期

- 键盘与触摸提供同等权限；按钮至少 52px，窄屏优先 56px；
- 状态变化进入 `aria-live`，不能只靠颜色表达目标与污染；
- `prefers-reduced-motion` 下保留位置变化，但取消漂浮、闪烁和装饰性摇摆；
- `visibilitychange`、失焦与重开需清空按键状态，防止粘键；
- 完成态展示三只配方瓶和共同完成文案，不产生双人排名。

## 7. 浏览器标准依据

- 动画循环遵循 WHATWG HTML 的 [Animation frames](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#animation-frames)，但游戏结果仍由固定整数 tick 决定；
- 物理键映射使用 W3C UI Events 的 [KeyboardEvent code values](https://www.w3.org/TR/uievents-code/)，使 `KeyA`、`KeyD` 与箭头键不受键盘布局字符影响；
- 键盘操作、目标大小、状态提示、颜色之外的信息和降动效以 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 为验收基线。

## 9. 风险与进入规格的 Gate

| 风险 | 规格前必须冻结的处理 |
| --- | --- |
| 玩家不知道为什么失败 | 结算分别显示“漏接左/右配方滴”或“接到灰滴”，同时在舞台标记对应雨道 |
| 两人抢同一键盘发生键位冲突 | 规则使用离散 `keydown`，忽略 `repeat`；按钮也一按一格，不依赖同时长按 |
| 失败等待太久 | 每波约 4 秒，错误后提供立即重试；不增加动画惩罚 |
| 移动端舞台太窄 | 七道用百分比布局，控制区分列；320px 仍保持 52px 触控目标 |
| 视觉遮住边界关系 | 云朵左右把手、当前闭区间和七条雨道必须比装饰背景拥有更高对比度 |
| 两端交叉导致非法状态 | reducer 在每个动作上维护 `leftLane <= rightLane`，UI 不自行修正 |
