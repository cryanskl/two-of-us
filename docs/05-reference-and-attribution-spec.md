# 借鉴与来源声明规范

## 1. 为什么单独声明

许可证文件回答“法律上允许做什么”，借鉴声明回答“这个作品实际上参考或使用了什么”。两者缺一不可。

即使只看过另一个项目的房间流程、计分方式或交接动画，没有复制一行代码，也应写明“仅借鉴机制”。这样以后重构、公开发布或排查相似实现时，不需要猜测来源。

## 2. 必须声明的情况

以下任一情况发生，都要进入作品 README 的“借鉴与来源声明”：

- 参考玩法规则、回合流程、交互或视觉结构；
- 参考目录、状态机、房间协议、算法或测试方法；
- 复制、翻译、修改或重写开源代码片段；
- 安装或打包第三方运行时、库、模型或组件；
- 使用第三方图片、字体、图标、音乐、音效、题库或模型权重；
- 由某个无许可证项目启发，但最终完全自行实现。

浏览器标准 API 和通用编程知识不必逐项声明；但实际阅读并依赖了某份示例实现时，应列出示例来源。

## 3. 借鉴类型

| 类型 | 含义 | README 必须说明 |
| --- | --- | --- |
| 玩法机制 | 只参考规则和体验，没有复制实现 | 参考了哪一部分，明确“未复制源码或素材” |
| 架构设计 | 参考状态机、房间、同步、目录或测试思路 | 哪些结构被重写，哪些没有采用 |
| 修改代码 | 复制后修改、移植或翻译代码 | 原文件/commit、许可证、主要修改 |
| 第三方依赖 | 通过 npm、WASM、本地运行时等使用 | 包名、版本、许可证、是否随作品分发 |
| 模型与素材 | 使用模型权重、图片、字体、音频、题库等 | 精确来源、许可证、署名和再分发边界 |

## 4. README 标准模板

每个作品 README 至少包含：

```markdown
## 借鉴与来源声明

| 项目 | 原作者与来源 | 借鉴类型 | 本作品实际使用 | 许可证 | 本仓库的处理 |
| --- | --- | --- | --- | --- | --- |
| Example | [author/project](https://github.com/author/project) | 玩法机制 | 仅参考交接流程，未复制源码或素材 | MIT | 重新设计状态机和界面 |

### 独立实现说明

除上表明确列出的依赖、代码和素材外，本作品的业务逻辑、文案与视觉均在本仓库内独立实现。
```

“独立实现说明”必须符合事实。如果使用代码生成工具或多个参考项目，也不能用一句“完全原创”覆盖真实来源。

## 5. 证据与版本

- 链接优先指向原始仓库，不指向聚合页或不明 fork；
- 正式引入代码、依赖、模型或素材时固定 tag、版本或 commit；
- 许可证链接指向对应版本的 `LICENSE`、`COPYING`、`NOTICE` 或模型卡；
- 若同一项目的代码与素材采用不同许可证，分成两行或明确分别说明；
- 对 Apache-2.0 的适用 `NOTICE`、GPL/AGPL/MPL 的源码义务和 Creative Commons 的署名要求，继续保留原始文件。

## 6. 无许可证项目

无许可证项目可以出现在声明中，但借鉴类型只能是“玩法机制”或抽象的“架构思路”。声明应明确：

> 该项目未声明许可证；本作品仅参考公开玩法描述，未复制其源码、文案、视觉素材或题库。

如果无法把“灵感”与具体表达分开，就暂停实现，直到获得作者授权或找到许可证明确的替代来源。

## 7. 验收 Gate

- 调研记录中标记为“参考”的项目都能在对应作品 README 找到；
- README 声明与实际依赖锁文件、源码注释、素材目录一致；
- 不出现“MIT 项目”但没有作者/链接，也不出现“参考网络资料”等模糊表述；
- 删除某项依赖或参考后同步更新声明；
- 发布前从零审阅一次源码、模型和素材来源，不只沿用旧声明。
