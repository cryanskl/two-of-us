# 表情电影擂台：本地优先可行性与权利边界调研

> 候选：`emoji-movie-duel`
> 调研日期：2026-07-25
> 结论：**Conditional Go**
> 建议产品 ID：`four-symbol-film-duel`
> 建议中文名：**四符片名擂台**
> 建议分类：**双人对抗**
> 本地等级：**A 级，直接双击 HTML 可玩**

## 1. 执行结论

这个候选可以做，但不应直接制作“热门电影 Emoji 猜片名”。

建议把它收敛为：

- 完全原创的虚构片名题库；
- 每题固定四枚符号；
- 单设备轮流答题；
- 双方获得难度、类型和提示资源对称的题目；
- 猜对得分，有限的“聚光灯”提示会降低本题得分；
- 只使用 Unicode 字符，由本机系统字体渲染；
- 每枚符号同时维护项目原创的中文等价文本；
- 不包含真实电影片名、人物、台词、剧情梗概、海报、剧照、Logo、音乐或厂商 Emoji 图片。

因此，本项目的核心不是“识别真实影视 IP”，而是“从四个图形语义中解码一个原创虚构片名”。这样仍保留了电影联想、猜题和对抗感，也显著降低版权、商标、图像授权及离线依赖风险。

## 2. 为什么是 Conditional Go

原始候选写的是：

> 用限定 Emoji 拼电影提示，对方有限次数内猜片名。

这里有两个需要调整的地方。

第一，如果一名玩家负责出题，另一名玩家靠猜题得分，出题者在对抗模式下有动机故意给出含糊或错误提示。除非双方高度信任，否则规则本身无法保证公平。

第二，如果直接采用真实热门电影，题库会立即碰到真实片名、系列商标、剧情表达、角色形象、海报剧照和特定 Emoji 厂商图像等边界。单个片名可能不满足版权保护门槛，并不等于整套影视表达和商业识别都可以自由使用。

所以 Go 的条件是：

1. 第一版改为系统提供原创题目，玩家只负责解码；
2. 默认题库中的片名、简介、线索和干扰项全部原创；
3. 不复制或导出任何平台 Emoji 图片；
4. 题目按配对规则分给双方，保证难度和资源对称；
5. 无障碍文本与图形符号表达等价，不引入额外答案信息；
6. 全部资源随仓库分发，无网络、服务端、构建器和远程字体依赖。

如果无法满足以上条件，则应降级为 No-Go，而不是发布真实电影题库。

## 3. 与当前 58 个项目的重复审计

### 3.1 最接近的现有项目

| 现有项目 | 相似点 | 实质差异 | 重复风险 |
|---|---|---|---|
| `hot-seat-pictionary` | 单设备传递、隐藏信息、猜词 | 玩家自由绘画；合作累计分；线索由玩家生成 | 中 |
| `lan-pictionary` | 一方表达、一方猜测 | 双设备局域网；实时绘画协作 | 低 |
| `telegraph-codebook` | 符号序列、固定答案、选择解码 | 固定长短码本；合作玩法；重点是编码规则学习 | 高 |
| `secret-recipe-code` | 隐藏目标、反馈、轮换、计分 | 数值配方与结构化反馈；不是语义联想 | 中 |
| `compatibility-quiz` | 多选题、双方轮流、离线题库 | 比较彼此答案；重点是关系了解 | 中 |

### 3.2 不能采用的低差异版本

以下版本不值得进入生产：

- “四个 Emoji + 四个选项 + 猜真实电影”；
- 只有题面皮肤不同、规则完全等同普通四选一；
- 使用固定符号码本，让玩家机械翻译；
- 出题者可以随意输入线索，却没有公平约束；
- 只把 `telegraph-codebook` 的符号换成 Emoji；
- 只把 `compatibility-quiz` 的问题换成片名。

### 3.3 建议保留的独特机制

要与现有项目形成实质区分，第一版必须同时具备：

- **四符限制**：每题严格四枚符号，不是任意长度；
- **原创片名联想**：答案是原创虚构片名，不是固定码本翻译；
- **配对题组**：双方各答不同题，但题型、难度和干扰项结构对称；
- **有限提示经济**：每人整局只有固定数量的“聚光灯”；
- **提示有代价**：使用提示会消去一个干扰项，同时降低本题可得分；
- **单次作答**：每题只能提交一次，避免靠穷举取胜；
- **可复核题包**：题目、标签、难度和配对关系都在静态数据中可检查。

结论：按建议方案实现时，重复度可接受；若退化为普通 Emoji 四选一，则与现有项目差异不足。

## 4. 玩法方向比较

| 方向 | 描述 | 公平性 | 原创性 | 风险 | 结论 |
|---|---|---:|---:|---:|---|
| A. 玩家自由出题 | 一人拼 Emoji，另一人猜 | 低 | 高 | 恶意或含糊线索、答案争议 | 不采用 |
| B. 真实电影题库 | 系统展示 Emoji，玩家猜热门片名 | 高 | 低 | 影视表达、商标、题库来源 | 不采用 |
| C. 原创虚构片名题库 | 系统展示原创四符题，双方轮答 | 高 | 高 | 内容制作成本 | **采用** |

方向 C 的成本是需要自己编写和验证题库，但这是可控的劳动成本，也能形成项目真正值得沉淀的内容资产。

## 5. 影视内容的版权和商标边界

### 5.1 片名短语不是“通行证”

美国版权局 Circular 33 说明，名称、标题和短语通常不受版权保护。但这只回答了短文本自身是否构成版权作品，不代表围绕某部影片的其他表达可以自由复制。

美国版权局对电影作品的说明指出，电影属于视听作品；其可保护内容可能涉及影像、声音、对白、剧本、摄影、剪辑和音乐等。剧情简介、处理稿或剧本也属于文字内容。

因此：

- 不把“片名通常不受版权保护”解释成可以复制影片内容；
- 不从真实剧情、经典场景、人物造型或台词中提炼题面；
- 不复制第三方网站的题库、简介或答案解释；
- 不使用海报、剧照、片段、配乐、音效或角色图标；
- 不将著名角色或系列识别元素换成 Emoji 后视为“已经原创”。

### 5.2 商标仍需单独判断

美国专利商标局说明，单一创意作品的标题通常不能仅凭该标题注册为联邦商标，但系列作品标题可能具有商标功能；商标审查还会考虑近似标识和相关商品或服务造成混淆的可能性。

所以本项目不应得出“真实片名没有商标风险”的结论。更稳妥的默认策略是：

- 产品名、模式名和题库名使用原创名称；
- 默认题库不用真实电影或系列片名；
- 不使用工作室、系列、角色和流媒体平台的 Logo；
- 不通过整体外观暗示与某个影视品牌存在授权或合作；
- 发布前对最终产品名做一次商标和搜索引擎近似检查。

本调研不是法律意见；如未来要公开发行真实影视题包，应进行按地区、按作品和按素材的专门权利审查。

### 5.3 不采用“公版电影包”作为第一版捷径

公版状态具有地域和版本差异，同一故事还可能存在后续改编、修复版本、配乐、海报、角色商标和新译名等独立权利。为了一个轻量本地游戏引入逐部作品核验，并不划算。

第一版明确不提供：

- 公版电影包；
- 真实电影扩展包；
- 自动从在线影视数据库导入；
- 用户输入片名后自动抓取剧情或海报；
- 指向第三方题库的运行时链接。

## 6. Emoji 字符、字形和图像授权

### 6.1 Unicode 字符不等于厂商彩色图片

Unicode 官方“Emoji Images and Rights”页面明确区分了字符编码与图表中展示的彩色 Emoji 图像，并说明这些彩色图像通常由各平台厂商拥有。

因此项目只保存：

- Unicode 字符序列；
- 项目原创的稳定 token ID；
- 项目原创的中文语义标签；
- 项目原创的题目与片名数据。

项目不保存：

- Apple、Google、Microsoft、Samsung 等平台的 Emoji PNG、SVG 或截图；
- Unicode 图表中来自厂商的彩色字形图片；
- 第三方 Emoji 字体；
- 从聊天软件或网页截取的表情贴图；
- 把平台字形渲染到 Canvas 后再导出的资源。

### 6.2 平台显示差异

Unicode Emoji 技术标准定义字符和序列，但实际字形、颜色、细节和支持范围由平台实现决定。相同字符在不同系统上可能看起来不同，部分新字符还可能显示为空框。

单设备比赛有一个天然优势：同一局的两名玩家会看到同一系统、同一浏览器的字形，因此平台差异不会直接造成局内双方不对称。但它仍会影响：

- 不同电脑上的题意理解；
- 字形缺失；
- 方向和动作的视觉差异；
- 组合序列被拆开显示；
- 颜色或肤色细节造成额外暗示。

第一版采用保守的闭合符号表：

- 优先选用较早、支持稳定的单码点 Emoji；
- 允许少量带 VS16 的简单序列；
- 不使用旗帜；
- 不使用肤色修饰符；
- 不使用家庭、职业、性别等 ZWJ 组合；
- 不使用依赖左右朝向才能成立的题意；
- 不让颜色成为唯一线索；
- 不使用看起来高度相似、只能靠细节区分的符号；
- 不依赖动画 Emoji 或平台专属扩展；
- 每个符号都必须通过 macOS Safari/Chrome 和至少一种其他平台字形的人工语义检查。

### 6.3 Unicode 数据许可策略

Unicode 的软件和数据文件通常受 Unicode License v3 约束。但本项目不复制 Unicode 数据文件、CLDR 注释、Emoji 字体或图像，只在源代码中直接使用少量字符码点，并自行编写中文标签。

如果未来引入 Unicode 或 CLDR 数据文件，必须：

1. 固定具体数据版本；
2. 保留适用许可文件和版权声明；
3. 在借鉴声明中写明文件、版本、用途和改动；
4. 不把厂商 Emoji 图像误当作 Unicode 数据许可覆盖的内容。

第一版不需要引入这项依赖。

## 7. 原创题库策略

### 7.1 题库规模

建议第一版包含 32 张原创卡，分成 4 个静态题包。每个题包可完成一局：

- 每局 8 题；
- 双方各 4 题；
- 每个题包包含 4 对难度匹配题；
- 双方各自的难度分布相同；
- 双方各自覆盖相同的类型分布；
- 每题 1 个正确片名和 3 个原创干扰片名；
- 每题固定 4 个符号；
- 每题指定 1 个可被“聚光灯”排除的干扰项。

题包切换可以轮换内容，但不需要随机生成题目。静态题包更容易复核公平性、无歧义性和权利来源。

### 7.2 题目原创性记录

每张卡建议保存：

- `id`：稳定 ID；
- `packId`：题包；
- `pairId`：公平配对；
- `side`：A 或 B；
- `difficulty`：1–3；
- `genre`：项目自定义类型；
- `tokens`：四个 token ID；
- `answer`：原创虚构片名；
- `decoys`：三个原创干扰片名；
- `spotlightRemoves`：提示移除项；
- `rationale`：内部语义解释，不在答题前显示；
- `authorship`：`original-project-copy`；
- `reviewed`：人工复核状态。

`rationale` 用来做内容审查和争议复核，不应在游戏进行时泄露。

### 7.3 原创检查清单

每张卡发布前检查：

- 搜索片名是否与知名电影、系列、游戏或品牌高度重合；
- 搜索四符组合是否明显指向某个真实影视作品；
- 不包含真实人物、角色名、地名品牌化用法或台词；
- 干扰项与答案在长度、风格和可信度上相近；
- 四枚符号共同支持答案，不靠冷僻双关；
- 不同字形下仍能表达大致相同概念；
- 中文等价文本不会直接拼出答案；
- A/B 配对题的难度经至少两人盲测接近；
- 题目解释全部由本项目作者自行撰写。

## 8. 双人对抗公平性

### 8.1 规则建议

- 8 回合，A/B 交替作答；
- 每人答 4 题；
- 每题只能提交一次；
- 不使用提示并答对：2 分；
- 使用一次“聚光灯”后答对：1 分；
- 答错：0 分；
- 每人整局有 2 枚“聚光灯”；
- 每题最多使用 1 枚；
- “聚光灯”由题库预先指定，排除一个确定的错误选项；
- 最高分 8 分；
- 同分即平局，不用速度突然死亡打破平局。

不以速度决定胜负，原因是单设备轮流玩法中，读屏、认知速度、输入设备和交接动作都会影响计时公平性。

### 8.2 配对和抽题

一局使用一个完整题包，而不是从全部卡中独立随机抽取。题包内部已经人工配平：

- 相同难度分布；
- 相同类型分布；
- 相同答案长度区间；
- 相同干扰项数量；
- 相同提示次数；
- 相同回合先后结构。

可以随机选择题包，也可以让玩家选择题包，但不得打散后分别随机给两人，否则容易产生一方连续得到简单题的问题。

### 8.3 交接隐私

本玩法没有必须对另一方隐藏的自由输入内容。回合交接只需要：

1. 显示“请交给下一位”；
2. 点击“我准备好了”；
3. 再显示题面。

分数和剩余提示可一直公开，不需要复杂防偷看机制。

## 9. 无障碍和文本等价

W3C 的 WCAG 2.2 非文本内容指南及 H86 技术说明，明确把 Emoji 作为需要提供文本替代的场景。

第一版应做到：

- 每个 token 有项目原创中文标签，例如“火焰”“月亮”；
- 视觉 Emoji 节点使用 `aria-hidden="true"`；
- 同一 token 提供屏幕阅读器可读的中文等价文本；
- 四个 token 的可访问名称按视觉顺序朗读；
- 不把答案、类型或额外解释写进可访问名称；
- 选项是原生 `<button>`，保留清晰焦点；
- 分数变化和提示使用结果进入适度的状态区域；
- 不只用颜色区分当前玩家、正确、错误和提示状态；
- 支持键盘完成整局；
- 动效遵循减少动态效果偏好；
- 200% 缩放时不出现必须横向滚动才能作答的布局。

建议在开局前提供对双方同时生效的“文字等价模式”：

- 关闭时：视觉上只显示 Emoji，辅助技术仍读出等价标签；
- 开启时：每枚 Emoji 下方同时显示标签；
- 一局中不能只为一方单独开启；
- 模式不会改变计分、题目或提示数量。

这不是“泄露答案”，因为文本仅表达符号本身的规范语义，不提供组合解释。例如 `🔥` 的标签可以是“火焰”，不能写成“燃烧的爱情”。

## 10. `file://` 本地可行性

本项目可以达到 A 级本地运行：

- 一个 `index.html`；
- 相对路径加载本地 CSS 和经典脚本；
- 数据写在本地 JavaScript 常量中；
- 不使用 ES Module；
- 不使用 `fetch()`；
- 不使用网络字体；
- 不使用 CDN；
- 不使用后端；
- 不需要 npm 安装；
- 不要求 LocalStorage 才能完成游戏；
- 不需要剪贴板、摄像头、麦克风或文件系统权限。

允许使用 `localStorage` 保存非必要偏好，但必须捕获异常；存储不可用时整局仍可正常完成。第一版甚至可以完全不保存。

## 11. 开源借鉴与依赖结论

本调研没有选用任何开源游戏仓库作为实现参考。

建议实现方式为：

- 游戏规则独立设计；
- 题库和中文文案独立创作；
- HTML、CSS 和 JavaScript 独立实现；
- 零运行时第三方依赖；
- 零第三方图像、字体、音频和题库；
- 不复制 Unicode/CLDR 数据文件；
- 只依据公开标准理解字符、可访问性和浏览器行为。

因此，当前无需填写“参考仓库 + commit/tag + 许可证 + 借鉴范围”。生产 README 仍应保留“借鉴声明”章节，明确写：

> 本项目为独立实现，未复制第三方开源项目代码、素材或题库。标准与权利边界资料见研究文档。

如果实现阶段实际参考了新的开源仓库，必须先补充：

- 仓库固定 URL；
- commit SHA 或 tag；
- 许可证；
- 实际借鉴内容；
- 明确哪些代码、素材或题目没有复制。

## 12. 主要风险与停止条件

| 风险 | 影响 | 缓解 | 停止条件 |
|---|---|---|---|
| 题目被误认成真实电影 | 权利和品牌风险 | 全部原创并做名称检索 | 无法消除明显指向 |
| 平台 Emoji 含义偏移 | 可玩性下降 | 闭合符号表、等价文本、跨平台审查 | 核心题依赖特定厂商字形 |
| 双方题目难度不均 | 对抗不公平 | 成对题包、盲测、固定分配 | 无法形成稳定配对 |
| 玩法退化成普通四选一 | 与现有项目重复 | 四符限制、提示经济、配对题组 | 核心机制任一被删减 |
| 无障碍标签泄露答案 | 破坏挑战 | 标签只描述 token，不解释组合 | 等价文本必须包含答案语义 |
| 题库内容成本过高 | 实现延期 | 第一版固定 32 卡，不做生成器 | 无法完成至少 4 个完整题包 |
