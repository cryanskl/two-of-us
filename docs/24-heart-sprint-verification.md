## 2. C 级启动与网络边界

作品通过仓库共享的 Socket.IO 本地运行时启动；页面只加载本机的样式、应用模块、逻辑模块、协议模块、双人席位模块和已固定的 Socket.IO 客户端。资源树没有远程字体、图片、视频、统计、公共 WebSocket 或第三方 API。

源码扫描未发现 `fetch`、XHR、localStorage、sessionStorage、IndexedDB 或 Service Worker。比赛数据只在当前房间中交换，不落盘；断线、刷新和成员变化会废弃半局状态。C 级必须由 `start.command` / `start.bat` 启动，直接打开 `file://` 时会明确提示使用本地启动器。

## 3. Chrome 双端真实流程

使用两个真实 Chrome 标签分别模拟主机与同伴，完成以下流程：

1. “小云”创建房间，“阿岚”通过五位房间码加入；只有主机可见且可用“开始比赛”；
2. 主机开始后，两端同时显示 `3`，点击按钮禁用；倒数完成后两端进入 `racing`；
3. 第一局主机完成 30 次有效点击，两端冻结为 `30 / 0`、比分 `1 : 0`；
4. 第二局同伴获胜，两端显示 `0 / 30`、比分 `1 : 1`；
5. 决胜局主机获胜，两端进入 `match-ended`、比分 `2 : 1`，相对自己的胜负文案正确；
6. “再来一场”把局号、比分、进度与本地输入序号重置，并重新进入三秒倒数；
7. 同伴中途离开后，主机立即回到等待态并清空比分；新同伴加入后从 `0 : 0` 开始；
8. 原主机离开后，剩余成员被提升为主机；第三个浏览器加入后只能开始全新比赛，不继承半局；
9. 主机与移动端控制台的 warning 和 error 均为 0。

客机刚加入但尚未收到首份公开状态时会发送 `heart-sprint:sync-request`。这是为关闭“成员事件先于状态事件到达”的顺序窗口而增加的最小协议动作；它不改变主机权威，也不允许客机提交完整状态。

## 5. 视觉忠实度

最终桌面与 390×844 截图已分别和两张冻结概念图逐张比较：

1. **色彩**：深紫黑背景、珊瑚第一席、青色第二席和暖象牙字与冻结 token 一致；
2. **信息层级**：标题与房间码在顶栏，比分嵌入赛场上部，主控制位于赛道下方；
3. **空间语义**：两条开放水平跑道共用棋盘格终点，没有变成卡片列表；
4. **视觉签名**：代码原生心形跑者、运动腿和计时牌式数字承担识别，不使用位图角色；
5. **实时状态**：连接灯、两个席位灯、进度、局号和相对胜负文案都由真实房间状态驱动；
6. **控制层级**：只有当前设备的大按钮是主动作，倒数与非比赛阶段真实禁用；
7. **响应式**：移动端仍保留横向赛道与 132px 拇指热区，桌面短视口保持一屏可玩；
8. **减少动态效果**：320×700 下模拟 `prefers-reduced-motion: reduce` 后过渡与动画均压缩至约 `0.00001s`，点击仍将进度从 7 推进到 8。

实现相对概念图的有意差异只有动态房间码、玩家昵称和实时比分，以及用系统字形绘制心形跑者；没有把概念图作为运行资产。Chrome 原生内容区为 1269×774，浏览器控制层无法把桌面窗口提升到概念原始 1586×992，因此桌面实现比概念更紧凑；移动端使用真实设备指标验证。两种尺寸均保留冻结构图和完整主流程。
