# A 级“把两边，拉成我们”定向调研

调研日期：2026-07-21

对应创意：`C14 同心拉链`

建议目录：`experiences/co-op/together-zipper/`

建议等级：A（同屏双人、`file://` 直开、无第三方运行依赖）

## 1. 调研结论

这个题目适合实现为一段不计分、不淘汰的双人节拍合作：左席守住拉链左侧，右席守住右侧；每一颗链齿都要两个人在同一个时间窗内各拉一次，才能把分开的布面逐段合上。

它不应依赖音乐谱面、连续物理或随机节拍。正式方向应采用 **固定整数 tick 的逐齿同步**：

- 全局规则以 30Hz 整数 tick 推进，动画位置不参与判定；
- 左席使用 `F`，右席使用 `J`，触控端各有一个原生按钮；
- 每颗齿只接收每席第一次有效拉动，重复输入是确定性的 no-op；
- 两次拉动都位于本齿时间窗，且彼此间隔不超过同步阈值，才算合齿；
- 过早、漏掉任一侧或两侧相隔过远都会卡住，但只重试当前齿；
- 三段共 15 颗齿，节奏逐段收紧；完成页只总结共同尝试，不排名、不比较谁更准。

这套规则让“共同完成”成为 reducer 可证明的权限条件，同时保持双击 HTML、键盘和触控都可用。

## 2. Brainstorm：四个方向与取舍

### 方向 A：音乐驱动的双人音游

以歌曲或节拍音轨作为时间源，左右玩家按谱面击打。这种方向很直观，但会引入自动播放限制、音频版权、谱面授权与设备音频延迟；没有声音时也很难保持完整体验。

**结论：不采用。** 本作不打包音频，视觉节拍本身就是完整规则。

### 方向 B：连续拉链物理

两个人持续拖动左右把手，通过布料张力、碰撞和惯性把拉链拉上。视觉上更像真实拉链，但连续输入、触摸采样、帧率和碰撞误差会使公平性与重放结果不稳定，也会与仓库已有双端运输玩法接近。

**结论：不采用。**

### 方向 C：随机节拍挑战

每颗齿随机生成目标时刻或速度。它能制造变化，但同一局无法被稳定复盘，测试也不能证明完整路线；随机失败会让亲密合作变成运气惩罚。

**结论：不采用。**

### 方向 D：固定 tick 的逐齿同步

每颗齿有公开的目标 tick、允许时间窗和双人同步阈值。两席各提交一次输入，成功后进入短反馈再前往下一齿；失败只重试当前齿。所有输入可记录、重放和测试。

**结论：采用，进入规格冻结。**

## 3. 机制草案

### 3.1 三段拉链

| 段落 | 齿数 | 目标 tick | 允许窗口 | 两席最大间隔 | 体验意图 |
| --- | ---: | ---: | ---: | ---: | --- |
| 起针·并肩 | 4 | 42 | `±9` | 5 tick | 熟悉左右各拉一次 |
| 穿雨·同拍 | 5 | 36 | `±8` | 4 tick | 稳住较紧的共同节拍 |
| 收尾·归心 | 6 | 30 | `±7` | 3 tick | 用最短同步窗完成合拢 |

每颗齿开始时 `beatTick = 0`。目标 tick 与窗口均为规则数据，而不是从 CSS 动画位置读取。

### 3.2 单颗齿判定

- 玩家在开放窗口之前拉动：立即产生 `early-left` 或 `early-right`；
- 某席第一次在窗口内拉动：记录其整数 tick；
- 同一席再次拉动：忽略，不覆盖第一次时间；
- 两席都已拉动，且 tick 差不超过同步阈值：成功；
- 两席都已拉动，但 tick 差超过同步阈值：`apart`；
- 窗口结束仍缺左席、右席或两席：`missed-left`、`missed-right` 或 `missed-both`；
- 失败增加当前齿的尝试数，保留此前已合好的齿，短反馈后重试同一齿。

边界必须在正式规格中冻结为明确的闭区间与判定顺序，避免“刚好卡在最后一 tick”由调用顺序决定。

### 3.3 状态机候选

建议使用七个显式阶段：

1. `intro`：规则与控制说明；
2. `section-intro`：本段节奏预告；
3. `playing`：接收 `PULL` 与 `STEP`；
4. `tooth-result`：成功反馈；
5. `jammed`：失败原因与原齿重试反馈；
6. `section-result`：本段共同汇总；
7. `complete`：15 齿完成与结语。

动作候选为 `START`、`BEGIN_SECTION`、`PULL { seat }`、`STEP { ticks }`、`NEXT_SECTION` 与 `RESTART`。`STEP.ticks` 必须采用小范围整数白名单，外部时间不能直接写入状态。

## 4. 合作必要性与确定性证明

对任一颗齿：

1. 成功谓词要求 `leftPullTick` 与 `rightPullTick` 都存在；
2. 左席只能写左记录，右席只能写右记录；
3. 固定任一席完全不输入，窗口结束必然进入对应 `missed-*`；
4. 单席重复输入不会代替另一席，也不会刷新自己的第一次时间；
5. 所以任一玩家都无法单独完成一颗齿，更无法独自完成 15 齿路线。

对确定性：

- 同一初始状态、配置与 action 序列必须得到相同结果；
- `requestAnimationFrame` 只把经过时间累积成固定 `STEP`，不直接决定成功；
- 页面隐藏或窗口失焦时停止累积，恢复后不追赶丢失时间；
- 键盘 `repeat` 在应用层被拒绝，规则层仍以“一席一次”为最终防线；
- 关卡不使用随机数、Date、音频时钟或存储状态。

## 5. 本地实现可行性

- 纯 HTML、CSS 与经典脚本，不使用 ES Module、`fetch()`、服务端、数据库或网络；
- 不使用第三方运行库，图片只承担氛围和纪念物，不保存节拍答案；
- 规则层为纯 reducer，可在 Node 内直接加载并重放；
- 视觉层使用 DOM/CSS 生成齿、刻度、进度和控制状态；
- 触控采用 `pointerdown`，键盘采用物理 `KeyboardEvent.code` 的 `KeyF` / `KeyJ`；
- 双击 `index.html` 即可完整游玩，因此属于 A 级。

## 7. 浏览器标准依据

- 动画循环遵循 WHATWG HTML 的 [Animation frames](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#animation-frames)，但规则只消费固定整数 tick；
- 物理键映射使用 W3C UI Events 的 [KeyboardEvent code values](https://www.w3.org/TR/uievents-code/)，避免键盘布局字符影响左右席；
- 隐藏和恢复行为依据 W3C [Page Visibility](https://www.w3.org/TR/page-visibility-2/)，恢复后不补算后台时间；
- 触摸与鼠标统一依据 W3C [Pointer Events](https://www.w3.org/TR/pointerevents3/)，每次按下只提交一次离散意图；
- 语义、焦点、状态提示、颜色之外的信息和降动效以 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 为验收基线。

## 9. 风险与进入规格的 Gate

| 风险 | 规格前必须冻结的处理 |
| --- | --- |
| 窗口边界因事件顺序产生歧义 | 冻结 `PULL` 与 `STEP` 的闭区间、结算顺序和最后一 tick 测试 |
| 动画节流导致恢复后瞬间失败 | `hidden` / `blur` 停止 RAF 累积，恢复后重置时钟且不追赶 |
| 长按或系统重复键制造多次输入 | UI 拒绝 `event.repeat`，规则拒绝同席第二次 `PULL` |
| 一个人连续敲两键冒充双人 | 这是同机信任边界；规则保证角色权限与两份输入，不做身份识别或监控 |
| 失败信息只靠颜色 | 文本明确区分过早、缺左、缺右、两边都缺与相隔太远 |
| 320px 上双席按钮拥挤 | 两个按钮保持至少 56px，舞台与控制上下排布，允许必要纵向滚动 |
| 参考音游带来音乐版权误解 | 生产目录零音频；声明明确仓库许可证不等于第三方媒体授权 |
