# C 级「心跳冲刺」手机控制器实时对抗规格

> 建立日期：2026-07-17 · 状态：已实现并验收 · 目标入口：`experiences/versus/heart-sprint/`

## 1. 本批要补齐什么

仓库已经覆盖 C 级同时按住、画布同步、轮流棋类、密封选择与密封问答，但还没有验证“手机作为高频实时控制器”的同局对抗。`心跳冲刺` 用一个非常小的玩法验证这条边界：两个人在同一局域网房间内，各自连续点击自己的按钮推动一名心形跑者；先到终点者赢下一局，先赢两局者赢得整场比赛。

本批主分类为“双人对抗”，启动等级为 C：必须由根本地运行时托管页面与 Socket.IO，两个浏览器加入同一房间；游玩过程不需要账号、云服务或公网。

## 2. Brainstorm 与取舍

| 方向 | 能补齐的能力 | 首版风险 | 决定 |
| --- | --- | --- | --- |
| A 级同心机关迷宫 | 同机实时合作、碰撞与机关 | 主要复用刚完成的固定步长输入，没有扩展局域网能力 | 保留为下一项低依赖候选 |
| B 级吹灭愿望 | 麦克风权限、Web Audio 与降级入口 | 需要真实声学环境校准，偏单人惊喜 | 后续单独验证媒体权限 |
| C 级手机控制器冲刺 | 高频离散输入、主机权威、移动端控制面 | 必须处理重复输入、局末冻结与主机迁移 | **本批采用** |
| D 级同频手势 | 首个模型、WASM 与摄像头能力包 | 模型分发方式仍会改变安装与许可证边界 | 等能力包决策后再做 |

最小版本只包含：创建/加入房间、两人就绪、三秒倒数、连续点击冲刺、三局两胜、下一局和再来一场。首版不加入机器人、账号、排行榜、震动、音效、道具、局外自定义、第三位观众或公网房间。

## 4. 用户流程

### 4.1 启动与加入

1. 用户双击根 `start.command` / `start.bat`，从门户进入“心跳冲刺”；
2. 页面连接共享 Socket.IO；直开 `file://` 时只显示 C 级启动说明，不伪装可玩；
3. 一人填写昵称并创建房间，页面显示五位房间码；
4. 另一人在同一局域网打开相同入口，填写昵称和房间码加入；
5. 两个席位齐全后，主机可点击“开始比赛”；同伴看到“等待主机开始”。

### 4.2 比赛

1. 主机发出 `3 → 2 → 1` 三段倒数状态；倒数期间控制按钮禁用；
2. 进入比赛后，两端各自点击“为我加速”；每次有效点击只推动自己的跑者一步；
3. 先累计 30 次有效点击者赢下一局，局末立即冻结后续输入；
4. 主机点击“下一局”再次倒数；先赢两局者进入整场结束；
5. 主机点击“再来一场”后，比分、进度和输入序号全部重新开始。

若比赛中任意成员离开，当前局作废并回到等待第二人的状态；剩余成员若被房间运行时提升为新主机，也只能在新同伴加入后开始全新比赛，不继承半局优势。

## 5. 权威状态机

### 5.1 状态结构

纯逻辑状态至少包含：

```js
{
  schemaVersion: 1,
  version: 1,
  phase: "waiting" | "countdown" | "racing" | "round-ended" | "match-ended",
  memberIds: [hostId, guestId],
  roundNumber: 1,
  countdown: null | 3 | 2 | 1,
  progress: { [hostId]: 0, [guestId]: 0 },
  scores: { [hostId]: 0, [guestId]: 0 },
  lastInputSeq: { [hostId]: 0, [guestId]: 0 },
  lastAcceptedAt: { [hostId]: 0, [guestId]: 0 },
  roundWinnerId: null,
  matchWinnerId: null
}
```

`version` 每次公开状态改变都严格递增。`progress` 上限为 30，`scores` 上限为 2。只有主机能创建、推进和广播权威状态；同伴只接受当前已知主机、当前房间、成员顺序一致且版本更新的状态信封。

### 5.2 输入信封

每端为自己的点击维护会话内单调序号：

```js
{
  roomId,
  type: "heart-sprint:tap",
  data: { inputSeq: 17 }
}
```

共享运行时重建 `senderId`，浏览器自报的身份不可信。主机只接受同时满足以下条件的点击：

- `phase === "racing"`；
- `senderId` 属于当前冻结的两个成员；
- `inputSeq` 是安全整数，且严格大于该成员的 `lastInputSeq`；
- 距该成员上次被接受的点击至少 30ms；
- 本局尚未产生赢家。

被节流的输入仍更新已观察序号，防止旧包随后重放；只有被接受的输入增加进度。Socket.IO 在单连接上可靠且有序，但单调序号仍能让 reducer 在测试、重连与异常重复消息下保持幂等。

### 5.3 终点原子性

主机 JavaScript 事件循环按事件逐个调用 reducer。某次有效点击把进度推进到 30 时，在同一个 reducer 返回值中同时：

1. 将进度封顶；
2. 写入 `roundWinnerId`；
3. 增加该成员比分；
4. 把阶段切到 `round-ended` 或 `match-ended`；
5. 必要时写入 `matchWinnerId`。

之后到达的点击因阶段已改变而被忽略，因此不会出现双方同时各得一分或两个客户端自报不同赢家。

### 5.4 倒数

不同设备的 `performance.now()` 和系统时钟不可比较，因此不广播“某个本地时钟的截止时间”。主机每秒广播一次带 `countdown: 3/2/1` 的完整状态，最后广播 `phase: "racing"`。客户端只展示收到的权威数字，不自行推断比赛已经开始。

## 6. 房间与主机迁移 Gate

- 继续复用 `shared/runtime/two-player-membership.js`，只有前两个成员是参与者；
- `room:state` 是成员身份与主机角色的唯一来源；
- 新主机由运行时提升后，客户端以自己持有的最近公开状态为参考创建新的 `waiting` 状态，并清空当前比赛；
- 主机发布 `heart-sprint:state`，同伴用 `senderId === knownHostId`、`roomId`、成员顺序和版本四层校验；
- 旧主机、第三人、旧房间或倒退版本的公开状态全部拒绝；
- 离开、断线和 `beforeunload` 都走现有 `room:leave` / 运行时清理路径。

## 7. 视觉系统

### 7.1 冻结方向

概念采用“夜间自行车馆计时牌”：深紫黑真实背景、一条开放式椭圆赛道、珊瑚与青色两条跑道、暖象牙色字和模拟七段计分。浪漫感来自成对颜色与共同赛场，不使用散落爱心、卡通吉祥物或庆祝彩屑。

建议设计 token：

| Token | 值 | 用途 |
| --- | --- | --- |
| `--bg` | `#080612` | 页面与赛场真实深色背景 |
| `--surface` | `#100b1d` | 大赛场的轻微层次，不做浮动卡片 |
| `--ink` | `#f5dfb1` | 标题、比分和主要文字 |
| `--muted` | `#9f8fa7` | 辅助说明 |
| `--coral` | `#ff6258` | 第一席、主机跑者与控制按钮 |
| `--cyan` | `#57d6e2` | 第二席、同伴跑者 |
| `--line` | `#49354f` | 赛道刻度与分隔线 |
| `--online` | `#31d37c` | 两人在线状态 |

字体只用系统栈，不新增远程字体：标题使用窄体倾向的 `"Arial Narrow", "PingFang SC", sans-serif`；正文使用 `system-ui, "PingFang SC", sans-serif`；比分使用 `ui-monospace, "SFMono-Regular", monospace`。所有按钮显式定义字体、字号和行高。

### 7.2 桌面构图

- 安全画布按概念原始 1586×992 的比例提取，但实现必须适配常见 1280×800；
- 顶栏只包含“回到作品库”、标题、房间码和在线状态；
- 比分嵌入赛场上部，不创建单独统计卡；
- 两条水平赛道共用一条棋盘格终点线；跑者为代码原生心形符号和运动线，不引入位图角色；
- 当前设备的大按钮居中放在赛场下缘，最小高度 112px；
- 页面首屏不出现额外标签、说明卡或第二主按钮。

### 7.3 移动构图

- 390×844 时顶栏、比分、两条赛道、在线状态和控制按钮按纵向顺序排列；
- 控制按钮位于拇指热区，最小高度 132px、宽度不小于可视区减 32px；
- 跑道保持横向，不把两名玩家改成左右窄列；
- 允许页面在 320×700 时纵向滚动，但不得横向溢出、裁掉房间码或让按钮小于 88px；
- 触控使用 `touch-action: manipulation`，点击不触发文本选择和双击缩放副作用。

### 7.4 状态与动效

- 等待态：跑者停在起点，主机显示“开始比赛”，同伴显示等待文案；
- 倒数态：赛场中央只突出一个大数字，控制按钮禁用；
- 比赛态：每次本地点击给按钮一次 90ms 压缩反馈，权威进度更新跑者位置；
- 局末：赢家跑者保持终点，赛道文字显示结果，主机按钮变为“下一局”；
- 整场结束：比分保持，主机按钮变为“再来一场”；
- `prefers-reduced-motion: reduce` 下移除运动拖影、缩放和过渡，但位置、比分与结果仍完整可见。

```text
experiences/versus/heart-sprint/
├── index.html              # C 级说明、lobby 与比赛页面结构
├── styles.css              # 冻结视觉 token、响应式和状态样式
├── logic.js                # 纯权威状态机与输入 reducer
├── logic.test.js
├── protocol.js             # 主机信封、成员与版本校验
├── protocol.test.js
├── app.js                  # Socket.IO、倒数调度、DOM 与输入绑定
└── README.md               # 启动、玩法、隐私、借鉴与限制
```

`logic.js` 和 `protocol.js` 使用 ES Modules，因为 C 级页面只在本地 HTTP 运行；不为 `file://` 伪造兼容层。具体玩法逻辑不进入 `shared/`，共享层只保留房间、席位与传输能力。

## 9. 隐私与网络边界

- 页面只发送昵称、房间码、成员 ID、点击序号、进度、比分和阶段；
- 不发送照片、麦克风、摄像头、地理位置、联系人或设备标识；
- 不写 `localStorage`、IndexedDB、Cookie 或云数据库；刷新后身份与比赛状态不保证恢复；
- 运行时只监听本机与局域网，不连接公共 WebSocket、统计、CDN、STUN/TURN 或第三方 API；
- 房间码是局域网便利入口，不是身份认证或互联网级秘密。

## 10. 自动化验收

### 10.1 纯逻辑

- 两个不同成员才能创建状态；
- 等待、三段倒数、比赛、局末和整场结束转移正确；
- 每次有效点击只增加一步；重复、倒退、过快、非成员和非比赛态输入不增加进度；
- 被节流序号不会在稍后重放；
- 第 30 步原子冻结赢家和比分；
- 先赢两局进入整场结束；
- 下一局保留比分并清空进度；再来一场清空全部比赛数据；
- 成员变化和主机迁移回到全新等待态。

### 10.2 协议

- 只接受当前房间、当前主机、当前两位成员和更高版本的公开状态；
- 拒绝旧主机、第三人、其他房间、成员顺序变化、无效结构和版本回退；
- 状态克隆不共享可变的 `progress`、`scores` 与序号对象。

### 10.3 仓库

- catalog 标记 `level: "C"`、`networkRequired: false`、两人双设备；
- verifier 能找到入口、README、相对 CSS/JS 与本地 `/socket.io/socket.io.js`；
- 源码扫描没有 CDN、公共 WebSocket、`fetch()` 外部资源或隐式存储；
- `npm test`、`npm run verify`、所有新增 JS `node --check` 与 `git diff --check` 通过。

## 11. Chrome 实玩验收

使用两个受控浏览器页面模拟两台局域网设备，至少完成：

1. A 创建房间，B 通过房间码加入，双方昵称和席位一致；
2. 同伴不能启动、下一局或重开比赛；
3. 三段倒数期间点击无效；
4. 第一局 A 连续点击获胜，第二局 B 获胜，第三局由其中一方完成整场；
5. 局末额外点击不会改变进度或比分；
6. 比赛中 B 离开，A 回到等待态；B 重新加入后从 0:0 新比赛开始；
7. 主机离开后剩余成员成为新主机，但旧半局不延续；
8. 桌面当前视口、概念原始桌面比例、390×844 和 320×700 无横向溢出；
9. 减少动态效果时核心流程仍可完成；
10. 浏览器日志无页面错误，Network/资源清单只有本地页面、Socket.IO 和仓库资源。
