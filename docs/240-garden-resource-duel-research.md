- 调研日期：2026-07-24

- 稳定工作 ID：`garden-resource-duel`
- 暂定体验名：`这一朵，我先养开`
- 建议目录：`experiences/versus/garden-resource-duel/`
- 建议启动等级：A（双击 `index.html`，无安装、服务、权限或公网）

## 1. 结论

V12 适合成为下一款双人对抗作品，但不能做成“阳光克雨露、雨露克虫害、虫害克
阳光”的换皮猜拳，也不能把已有的合作花园改成互相扣分。

推荐进入规格的版本是一场最多六回合的单设备热座赛：

- 每人有完全相同的六张一次性手牌：2 张阳光、2 张雨露、2 张虫害；
- 公共季节牌堆恰有 3 次“需要阳光”和 3 次“需要雨露”，开局用公开 seed
  确定顺序，每回合只揭示当前需求；
- 每回合两人依次接管设备，秘密选择一张未用手牌；
- 资源牌只有在匹配当前需求且没有被对方虫害阻断时，才获得本轮花瓣；
- 虫害不偷取旧分、不产生自己的花瓣，只阻断对方本轮本来能获得的花瓣；
- 六轮花瓣价值依次为 `1, 1, 2, 2, 3, 3`，越晚使用资源牌越可能获利，也越容易
  被对方猜中；
- 先达到 5 花瓣者开花并获胜；同轮一起达到则平局；
- 六轮无人开花时比较花瓣，仍相同即平局。

核心闭环是：

```text
当前季节需求 + 双方公开的剩余手牌
                 ↓
        两份秘密的一次性选择
                 ↓
       同时揭晓、原子阻断与得分
                 ↓
   现在得小分 / 留牌争大分 / 用虫害读人
```

随机顺序只产生双方共同面对的环境，不给任何席位不同信息或数值。胜负完全来自
同一轮的两份选择和公开历史。

## 5. Brainstorm：四种方向

| 方向 | 核心规则 | 结论 |
| --- | --- | --- |
| 三向固定克制 | 阳光 / 雨露 / 虫害组成静态胜负表 | 排除；只是题材化猜拳 |
| 累计阳光与水 | 资源加到自己，虫害扣对方累计值，先到阈值 | 排除；容易全程破坏、软锁或靠隐藏 tie-break 收尾 |
| 三块花圃秘密分配 | 每轮把阳光、水和虫害分配到多个地块 | 暂缓；首局解释、目标选择和多地块状态过重 |
| 公共需求 + 有限手牌 | 资源匹配需求得花瓣，虫害只阻断当轮，牌用后消失 | **采用**；有限、可读、可穷举，且每轮选择价值随历史变化 |

早期试算排除了两个看似简单但实际失效的版本：

1. 每轮双方固定获得 `+1 阳光 / +1 水`、虫害只延迟奖励：理性路径几乎都会在
   第六轮一起达到阈值，虫害只是改记账时点；
2. 两张阳光、两张雨露、两张虫害，资源直接累计并允许提前开花：把两张虫害留到
   最后成为显著优势，虫害没有真实决策价值。

采用版本让公共需求和逐轮价值共同改变每张牌的机会成本。玩家知道剩余牌和已经
出现过几次阳光/雨露，但不知道季节牌堆的后续顺序。

## 6. 建议冻结的最小规则

```text
PLAYER_COUNT = 2
ROUND_COUNT = 6
HAND = sun × 2, water × 2, pest × 2
SEASON_DECK = sun × 3, water × 3
PETAL_VALUES = 1, 1, 2, 2, 3, 3
BLOOM_TARGET = 5
```

### 6.1 每轮

1. 公开本轮需求、花瓣值、双方得分与双方剩余手牌；
2. 本轮第一位玩家接管设备并秘密选择一张未用牌；
3. 页面卸载秘密选择，交给另一位玩家；
4. 第二位玩家秘密选择；
5. 公共页只说明“两张牌已封存”，不显示任何秘密；
6. 两人共同确认后，同时揭晓并原子结算。

每轮第一位选择者交替。顺序只影响谁先拿设备，不影响结算顺序。

### 6.2 联合结算

对每位玩家分别判断：

```text
playedMatchingResource =
  playedCard === currentSeasonNeed

blocked =
  opponentCard === pest

petalsEarned =
  playedMatchingResource && !blocked
    ? currentRoundPetalValue
    : 0
```

- 虫害对虫害：双方都不加分；
- 虫害对不匹配资源：双方都不加分，虫害被浪费；
- 虫害对匹配资源：资源方本轮加 0，虫害方也加 0；
- 两张匹配资源：双方都获得完整本轮花瓣；
- 两张不匹配资源：双方都不加分；
- 手牌在揭晓时才从双方公开库存扣除，但密封后不得改选；
- 虫害永不删除既有花瓣，也不把对方花瓣转给自己。

### 6.3 终局

- 一方本轮后达到至少 5 花瓣、另一方未达到：该方获胜；
- 双方同一轮达到至少 5 花瓣：平局；
- 第六轮后均未达到：花瓣更多者获胜；
- 花瓣相同：平局；
- 不用先选席位、最后操作时间、剩余牌种、随机 seed 或动画完成先后破平。

## 7. 机制穷举

每人的六张手牌共有：

```text
6! / (2! × 2! × 2!) = 90
```

公共季节牌堆共有：

```text
6! / (3! × 3!) = 20
```

按生产候选规则枚举 `90 × 90 × 20 = 162,000` 个“双方固定出牌序列 × 季节牌堆”
完整夹具，得到：

| 结果 | 数量 |
| --- | ---: |
| 席位 0 获胜 | 59,444 |
| 席位 1 获胜 | 59,444 |
| 平局 | 43,112 |

这证明在完全镜像输入下没有席位结算偏置。90 个固定出牌序列中，没有任何一个能
在全部对方序列与全部季节牌堆上保持不败。它不等于求解了玩家会根据公开历史调整
的完整信息集博弈；规格和测试只把“镜像、公平、有限、无固定无敌序列”作为首版
边界，不宣称数学最优平衡。

生产逻辑测试应直接复现这 162,000 个夹具，不能只把本文件中的统计数字当证据。

## 8. 单设备隐私与信任边界

热座遮屏的合格标准不是 `display:none`：

- 当前选择只在当前席位的选择页出现；
- 确认后，选择按钮、选中态、说明、可访问名称与 live region 全部退出 DOM；
- 交接页、等待揭晓页、URL、storage、`data-*`、事件详情和注释不得包含牌值；
- `blur`、页面隐藏、`pagehide` 和 Escape 立即遮屏并清除未确认草稿；
- 已确认的两份秘密只存在内存中的权威状态，直到显式揭晓；
- 公开 view 在 `ready-to-reveal` 阶段只能说“两位都选好了”；
- 只有进入 `round-result` 后，历史才公开本轮两张牌和结算。

它只承诺正常共同使用流程中不提前渲染秘密，不能抵御同一设备上主动使用开发者
工具、断点或 JavaScript 内存检查。README 必须明确这条信任边界，不能使用
“加密”“防作弊”或“绝对保密”等表述。

## 9. 可访问性与生命周期

- 三类手牌使用原生 `<button>`，文字同时写出名称、剩余数量和本轮可能作用；
- 不只靠黄色、蓝色、红色或花朵图形表达牌种、得分和是否被阻断；
- 支持 Tab、Shift+Tab、Enter、Space；可附加 `1 / 2 / 3` 快捷键；
- Escape 遮屏并清除未确认草稿；
- 点击目标优先达到 48×48 CSS px，并满足 WCAG 2.2 的最低目标尺寸要求；
- 焦点环可见；阶段切换后把焦点放到稳定标题或首个主要动作；
- `aria-live` 只播报公开阶段变化和揭晓结果，不播报秘密草稿；
- `prefers-reduced-motion: reduce` 下取消花瓣弹出、卡牌翻面和胜利脉冲；
- 强制颜色模式下牌种仍由文字与边框区分；
- 页面失焦、隐藏或恢复不会自动选牌、揭晓、扣牌、加分或推进回合；
- 规则不使用真实时间，动画完成事件不能成为状态迁移条件。
