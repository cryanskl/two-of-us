# 全网调研方法与判定口径

## 调研问题

本轮不是泛泛收集“情侣网站”，而是回答三个可执行问题：

1. 哪些现有开源项目可以合法地改造成纯本地 HTML？
2. 哪些成熟网页玩法适合情侣场景，但需要自行实现？
3. 下一批最值得做的作品是什么，为什么？

## 信息源优先级

1. 原作者 GitHub / GitLab 仓库及其中的 `LICENSE`、README、源码；
2. 项目官方文档或官方演示；
3. CodePen、itch.io 等原作者页面；
4. 文章、视频和聚合页仅用于发现线索，不作为许可证依据。

## 每个候选的记录字段

| 字段 | 说明 |
| --- | --- |
| 名称 | 项目名或清晰的创意名 |
| 分类 | 惊喜 / 合作 / 对抗 |
| 玩法 | 一句话说明实际交互 |
| 设备模式 | 单设备同屏 / 单设备轮流 / 双设备 |
| 离线等级 | A / B / C / D，定义见分类规范 |
| 技术形态 | 原生 HTML、Canvas、WebAudio、框架等 |
| 许可证 | MIT、GPL、未声明等 |
| 引入建议 | 可直接评估 / 适合重写 / 仅作灵感 |
| 改造成本 | 低 / 中 / 高 |
| 来源 | 原始仓库、官网或演示直链 |

## 推荐优先级

- **P0**：玩法明确、A 级离线、许可证清晰、移动端可用、改造成本低；
- **P1**：价值高，但需要资源本地化、构建或适配触屏；
- **P2**：值得保留的创意，需重写或存在许可证/联网限制；
- **不建议**：必须依赖后端、商业素材或高风险权限，且没有明显本地替代方案。

## 搜索与核验规则

- 搜索结果页只用于发现，最终链接回到一手来源；
- GitHub 项目的“可复制”结论必须以仓库许可证为准；
- README 宣称“开源”但没有许可证文件时，仍按“未声明许可证”处理；
- 在线 demo 能运行不代表 `file://` 能运行，需要检查模块加载、跨域请求和远程资源；
- 同一玩法的多个 fork 只保留来源更清楚、维护状态更好或技术更适合本地化的代表。
