# 「这一弹，拐弯见你」调研报告

> 候选 ID：`ricochet-tank-duel`
> 来源：V13「像素坦克折射战」
> 推荐结论：**有条件 Go**
> 推荐等级 / 分类：**A / 对战**

## 1. 结论先行

这个候选可以进入设计阶段，但成立条件比“做一个双人坦克小游戏”严格得多。

必须同时保留以下五项核心机制：

1. 两位玩家在同一设备上实时移动；
2. 双方输入在同一个固定步长内同时生效；
3. 场上允许存在多枚仍在飞行的弹体；
4. 弹体可以在边界和墙面上连续折射；
5. 同一逻辑刻发生的双方命中必须原子结算。

这五项共同构成相对于当前仓库已有项目的增量。如果实现阶段退化为轮流发射、只允许一次落地反弹、按玩家顺序更新、只做离散重叠检测，或把折射做成纯装饰，那么应当判定为 **No-Go**，而不是勉强交付一个与现有项目高度重叠的变体。

推荐公开标题为「这一弹，拐弯见你」。角色不采用真实坦克造型，而使用原创抽象几何“折光车”：圆角车身、方向箭头和双色轮廓。这样既保留玩法辨识度，也避免真实军事品牌、迷彩、武器型号或预制坦克素材。

## 2. 仓库现状与相邻项目审计

### 2.1 V13 原始意图

V13 的原始描述是：

> 两辆坦克隔墙移动，炮弹边界反弹，先命中规定次数者胜；单设备同屏，键盘；高复杂度；需要依赖。

调研后的目标仍然是本地点开即玩，但将“需要依赖”解释为研发复杂度提示，而不是运行时依赖。成品应为纯静态 HTML/CSS/JavaScript，在 `file://` 下工作，不要求安装包、服务器、网络、字体或外部素材。

### 2.2 与 `heart-catapult` 的差异

`heart-catapult` 是热座轮流制：

- 一方秘密选择角度和力度；
- 单枚投射物依次发射；
- 允许直击或一次地面反弹；
- 完整回合结束后共同计分。

本候选的不可替代增量是：

- 双方可同时移动、转向和开火；
- 同场允许多枚弹体；
- 墙面和边界可多次折射；
- 命中按同一逻辑刻原子结算；
- 主要决策来自实时走位、封线和反弹路线，而不是秘密参数竞猜。

若改成静止瞄准或轮流发射，就会显著回落到 `heart-catapult` 的骨架，应停止实现。

### 2.3 与 `light-trail-hunt` 的差异

`light-trail-hunt` 是自动前进的格点转向对抗，永久轨迹构成障碍，同刻相撞可以平局。

本候选不同在：

- 移动是连续空间中的前进、后退和旋转；
- 危险来自有寿命、有数量上限的弹体，不是永久轨迹；
- 场景墙体固定且镜像，不由玩家行走生成；
- 核心计算是连续碰撞与折射，不是下一个格点占用判断。

两者可共享“同刻结算必须公平”的原则，但不能共享玩法实现。

### 2.4 与 `soft-sumo` 的差异

`soft-sumo` 使用旋转、蓄力、释放冲刺和身体推动，在收缩圆形场地中将对方推出边界。

本候选明确排除：

- 车体之间的碰撞与推动；
- 蓄力冲刺；
- 收缩场地；
- 依靠身体接触决胜。

其核心是远程弹道规划、墙面折射和弹体压力管理。固定矩形地图与左右镜像活动区也和圆形相扑场形成清楚区分。

### 2.5 与 `paper-soccer` 的差异

`paper-soccer` 中的“反弹”是图上的旧节点或边界让玩家获得额外一步，本质是回合制图遍历。

本候选中的折射是物理意义上的：

- 弹体在一个逻辑刻内沿线段连续运动；
- 接触墙面时根据法向改变速度分量；
- 同一刻可能剩余时间继续运动并再次接触；
- 最早接触时间决定事件顺序。

二者只共享“反弹”这个词，不共享机制。

### 2.6 与 `echo-arena` 的差异

`echo-arena` 是热座式顺序记忆挑战，没有连续空间运动或弹体物理。

它对本候选的价值仅在于提示：

- 阶段状态必须清晰；
- 输入必须在阶段切换时正确清空；
- 结束条件和重开路径必须确定。

不构成机制重叠。

### 2.7 重叠审计结论

| 项目 | 主要决策 | 空间模型 | 时间模型 | “反弹”含义 | 本候选增量 |
|---|---|---|---|---|---|
| `heart-catapult` | 秘密角度 / 力度 | 静态炮台 | 轮流 | 至多一次地面反弹 | 实时走位、多弹、多墙折射 |
| `light-trail-hunt` | 转向与封路 | 离散格点 | 同步刻 | 无 | 连续运动、有限弹体 |
| `soft-sumo` | 冲刺与推挤 | 连续圆形场 | 同步刻 | 无 | 远程折射、无接触推动 |
| `paper-soccer` | 选择图边 | 图结构 | 回合制 | 额外一步 | 连续碰撞和法向反射 |
| `echo-arena` | 记忆顺序 | 无连续空间 | 热座阶段 | 无 | 实时空间瞄准与躲避 |

最终判断：**存在明确增量，因此有条件 Go。**

## 3. 技术调研

### 3.1 为什么离散碰撞不够

如果每个渲染帧只检查“弹体现在是否与墙或车体重叠”，高速弹体可能在两个采样位置之间穿过薄墙或目标，形成 tunneling（穿透）。

Tang、Kim、Manocha 的连续碰撞检测论文将问题描述为：离散采样可能漏掉两个配置之间发生的接触，而连续碰撞检测需要在运动区间中求出第一次接触时刻。对本项目而言，正确模型不是“移动后修正”，而是：

1. 对本逻辑刻剩余的运动线段求最早接触时间；
2. 将弹体推进到接触点；
3. 原子处理同一接触时刻的事件；
4. 若发生反射，用剩余时间继续求下一次接触；
5. 达到接触次数上限时安全销毁弹体。

Linahan 对球扫掠碰撞数值稳健性的讨论还说明：即使基本算法方向正确，浮点边界、穿入和抖动仍会产生不可靠结果。因此本项目应冻结整数定点格式、事件并列规则和零时间重复接触处理，而不能把这些细节留给浏览器浮点偶然性。

### 3.2 固定步长与确定性

推荐逻辑层固定为 60 tick/s，每次 `STEP` 只推进一个逻辑刻。渲染层可以使用 `requestAnimationFrame`，但其时间戳只能给累加器提供调度信息，不能直接成为游戏规则里的可变 `dt`。

确定性边界如下：

- 所有规则状态只在固定步长中修改；
- 同一 tick 先采集双方输入位掩码，再统一推进；
- 方向使用冻结的整数查找表，不在运行时调用三角函数；
- 地图、出生点、墙体和初始朝向固定；
- 不使用随机数；
- 输入日志应能重放并产生相同状态哈希；
- `performance.now()` 只用于调度，不进入逻辑状态。

Breitner 与 Smith 对 lock-step simulation 的讨论表明，给定相同初始状态和输入，得到一致演化需要对整个计算过程施加明确纪律。这里不做联网同步，但同一原则能用于测试复现、避免按玩家顺序更新产生偏差。

### 3.3 暂停与长帧

High Resolution Time 规范说明 `performance.now()` 提供单调时间来源；HTML 的 animation frame 回调提供时间戳；Page Visibility 规范则说明隐藏页面可能触发调度节流。

因此不能在标签页恢复后补算几秒钟游戏：

- 页面 `hidden`、窗口失焦、出现异常长帧时，两位玩家同时暂停；
- 清空所有持续按键和开火边沿；
- 丢弃累加器残留；
- 由玩家显式恢复，并经过统一的 3、2、1 倒计时；
- 单帧最多补算 5 个 tick；
- 帧间隔超过 250 ms 或积压超过上限时直接进入暂停，不做追赶。

这样既避免“恢复页面立即被击中”，也避免长帧导致不同设备出现不同结果。

### 3.4 连续碰撞的推荐表示

第一版只使用圆形运动体和轴对齐矩形墙：

- 车体：圆；
- 弹体：小圆；
- 墙体：轴对齐矩形；
- 世界边界：四条轴对齐边；
- 车体移动：圆对扩张矩形的扫掠；
- 弹体对墙：点对按弹体半径扩张后的矩形扫掠；
- 弹体对移动车体：相对速度下的圆对圆扫掠。

所有位置与速度使用 Q10 定点整数（`SCALE = 1024`）。比较碰撞时间时保留分子 / 分母形式，避免提前转回浮点。测试中可使用 `BigInt` 作为判定 oracle；运行时实现则必须在整数安全范围内，并对乘积范围写断言。

同一最早时刻的规则必须冻结：

- 命中目标优先于墙面反射；
- 同时接触两条垂直墙法向时，两个速度分量一起翻转；
- 拐角接触算一次反射；
- 并列表面使用固定 ID 排序；
- 反射后只接受沿新速度方向的“进入”接触，禁止零时间重复撞同一表面；
- 一枚弹体单 tick 最多处理 4 次接触，超出即以 `contact-cap` 原因销毁。

这套规则不是为了制造复杂性，而是为了让“擦角、夹缝和同刻命中”在所有设备上具有唯一答案。

### 3.5 弹体资源边界

为了让本地点开即玩、低端设备也能稳定运行，必须给弹体系统硬上限：

- 每位玩家最多 2 枚存活弹体；
- 开火冷却 24 tick（0.4 秒）；
- 每枚弹体寿命 360 个活跃 tick（6 秒）；
- 最多允许 3 次反射，第 4 次反射接触直接销毁；
- 单 tick 最多 4 次碰撞事件；
- 弹体之间不发生碰撞；
- 弹体不命中自己的发射者。

在最多 4 枚弹体、有限墙体和固定接触循环下，每个 tick 的计算量有清晰上界。弹体不互撞也避免把事件系统扩大为全局多体求解。

### 3.6 同刻双方命中

不能先更新左方，再更新右方，否则左方命中导致重置场景时，右方原本同刻应命中的弹体会消失。

推荐流程：

1. 推进两辆车体；
2. 收集所有弹体在本 tick 中的事件；
3. 求出本 tick 命中的目标集合 `hitSet`；
4. 每个目标在一个 tick 内最多被计一次；
5. 左方被命中，右方得 1 分；右方被命中，左方得 1 分；
6. 若双方同刻被命中，则双方同时得分；
7. 结算后统一清空弹体并重置回合；
8. 若双方同刻达到 3 分，整局结果为平局。

整局活跃时间上限为 5400 tick（90 秒）。到时高分者胜，同分平局，避免双方无限躲避。

### 3.7 对称地图与公平性

第一版只提供一张固定地图，不做随机生成或地图选择。地图关于竖直中线严格镜像：

- 墙体成镜像对；
- 出生位置成镜像对；
- 初始朝向互为镜像；
- 左右活动区面积一致；
- 至关键通道的最短路径、可见射线和典型折射路线成对出现。

“视觉上差不多”不足以证明公平。实现应提供机器可验证的镜像测试：

- 每个左侧墙体都有一个坐标精确镜像的右侧墙体；
- 镜像输入日志交换玩家后，状态哈希也应互为镜像；
- 至少准备直击、单折、双折三组成对 golden shot；
- 同一路径在镜像侧具有相同接触时刻、反射数与命中 tick。

车辆限制在左右镜像活动区，避免车体之间发生碰撞，也防止两位玩家争抢同一键盘区域时形成复杂近身遮挡。弹体仍可穿过中央通道进入对方区域。

## 4. 输入调研

### 4.1 键盘

建议键位：

- 左方：`W/S` 前进 / 后退，`A/D` 左转 / 右转，`F` 发射；
- 右方：方向键前进 / 后退 / 左转 / 右转，`Enter` 发射；
- `P` 或可聚焦按钮：暂停。

按键规则：

- 移动和旋转保存为 held state；
- 发射只接受从未按下到按下的边沿；
- 忽略 `KeyboardEvent.repeat` 产生的重复开火；
- `blur`、`visibilitychange`、暂停和重开时清空所有 held state；
- 不假设键盘一定支持任意多键并发，触屏按钮作为等价替代入口。

### 4.2 触屏和指针

Pointer Events 为鼠标、触控和笔提供统一事件模型，并提供 `pointerId` 与 pointer capture。每位玩家应有独立控制区，使用原生按钮构成方向 / 转向 / 发射控制：

- `pointerdown` 记录该按钮对应的 `pointerId`；
- `pointerup`、`pointercancel`、失去 capture 时都释放；
- 不使用 `pointermove` 的连续坐标直接驱动物理；
- 两侧控制区可以同时持有多个不同 `pointerId`；
- 按钮视觉和可点击面积至少 44×44 CSS px；
- 控件不能覆盖关键赛场信息。

这样能避免手指滑出按钮后“卡键”，也能让键盘与触控使用同一套输入位掩码。

## 5. 可访问性与减弱动态

### 5.1 不能把 Canvas 当作唯一信息源

画布之外应持续显示一个文本状态投影：

- 双方比分；
- 当前朝向（八方位文字）；
- 粗粒度位置（行 / 列区域）；
- 存活弹体数；
- 开火冷却状态；
- 最近来弹的大致方向与距离；
- 剩余时间；
- 暂停、倒计时与胜负结果。

高频位置变化不应逐 tick 通过 live region 播报。`role="status"` 只用于倒计时、暂停、命中、得分和结果等低频事件。若旁边的文本投影已经完整，画布可设为装饰性；否则必须用 `aria-describedby` 指向玩法与当前状态摘要。

需要诚实声明：实时空间躲避本身依赖持续运动感知，文本投影能改善理解和陪玩协作，但不能承诺对完全非视觉用户提供与视觉操作完全等价的竞技体验。这一点应作为验收限制，而不是用泛化的“无障碍支持”掩盖。

### 5.2 `prefers-reduced-motion`

减弱动态不能改变逻辑速度、弹体轨迹或碰撞结果，否则会让同场玩家看到不同规则。开启 `prefers-reduced-motion: reduce` 时：

- 去掉装饰尾迹；
- 去掉屏幕震动；
- 去掉命中闪白与缩放脉冲；
- 回合重置使用瞬时状态切换；
- 可关闭渲染插值，但逻辑刻不变；
- 保留弹体、车体和方向等玩法必需运动；
- 用静态文字与颜色边框补充命中反馈。

Media Queries Level 5 将该偏好描述为减少非必要运动。因此本项目应明确区分“玩法必需运动”和“装饰运动”，而不是简单隐藏弹体。

### 5.3 WCAG 相关要求

实现阶段至少落实：

- 所有按钮可键盘聚焦且有清晰焦点；
- 不以颜色作为唯一阵营标识，同时使用形状、标签与图案；
- 指针按下可取消，动作在释放时确认；
- 控件有足够目标尺寸与间距；
- 键盘、触控和鼠标入口能并存；
- 暂停和重开不抢焦点；
- 结果弹层后焦点进入可操作区域，关闭后回到合理位置。

## 6. 本地点开即玩约束

目标是直接双击入口 HTML 即可运行：

- 经典相对路径脚本，不使用 ES module；
- 不调用 `fetch()`；
- 不依赖本地服务；
- 不依赖 npm 运行时；
- 不读写服务端；
- 不加载外部字体、图片、音频或统计脚本；
- 不要求 `localStorage` 才能完成游戏；
- 所有视觉由 Canvas / CSS 原语绘制；
- 所有规则数据随源码发布。

npm 只作为仓库级开发与验证工具，不是玩家运行依赖。

## 7. 范围建议

### 7.1 第一版包含

- 一张固定镜像地图；
- 两位本地玩家；
- 键盘与双人触屏控制；
- 固定步长确定性模拟；
- 车体扫掠与滑墙；
- 弹体连续碰撞、多次折射；
- 同刻原子计分；
- 先到 3 分或 90 秒结算；
- 暂停 / 恢复 / 重开；
- reduced-motion 适配；
- 可见文本状态投影；
- 离线 `file://` 运行；
- 规则与确定性测试。

### 7.2 第一版排除

- AI 对手；
- 联机；
- 随机地图；
- 地图编辑器；
- 道具、生命值和不同武器；
- 车体碰撞与推动；
- 弹体互撞；
- 自伤；
- 音频素材；
- 粒子爆炸；
- 关卡、成长、皮肤和账号系统。

这些排除项能维持清楚的物理边界，也避免为了“坦克游戏”的品类想象而扩张。

## 8. Go / No-Go 门槛

### 8.1 进入实现的硬门槛

必须先通过：

1. 固定输入日志重放得到一致状态哈希；
2. 镜像输入交换玩家后得到镜像状态；
3. 高速弹体穿越薄墙 / 车体的 golden case 不穿透；
4. 拐角双法向、零时间重接触和单 tick 多次折射有唯一结果；
5. 双方同 tick 命中时双方都得分；
6. 弹体数量、寿命、反射数和单 tick 接触数都有硬上限；
7. 隐藏页面和长帧恢复不补算；
8. 键盘与多指触屏能映射到同一输入位掩码；
9. `file://`、断网和无缓存环境均可运行；
10. reduced-motion 不改变模拟结果。

### 8.2 应转为 No-Go 的情况

以下任一情况出现，应停止而不是降级交付：

- 用离散重叠检测代替连续碰撞；
- 左右玩家按顺序结算；
- 为省事改成轮流发射；
- 只允许一枚弹体且击中后立即轮换；
- 折射只剩一次地面反弹；
- 地图随机且无法证明公平；
- 依赖服务器或外部 CDN；
- 无法为触屏提供稳定的多指释放语义；
- 无法给实时视觉玩法提供最低限度的文本状态投影。

## 11. 推荐结论

**有条件 Go，推荐 ID `ricochet-tank-duel`，标题「这一弹，拐弯见你」，A 级、对战类。**

它值得做的原因不是“坦克”主题，而是仓库里尚未出现的组合：同屏实时走位、连续多弹、多墙折射、固定步长确定性和同刻双方命中的公平结算。后续 brainstorm、spec 和 plan 必须继续保护这一组合；一旦核心被削弱，就应回到 No-Go。
