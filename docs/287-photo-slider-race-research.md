# Photo Slider Race 调研

## 1. 结论

建议：**Go（带实现验收门槛）**。

推荐项目：

- ID：`photo-slider-race`
- 中文名：**同一张，谁先拼回**
- 分类：`versus`
- 等级：A（纯静态、本地点开即玩）
- 核心形式：同一设备、同一屏幕、两块相互独立但初始局面完全相同的 3×3 滑块拼图，双方同时竞速

它与现有 `photo-swap-puzzle` 的核心交互不同：后者是单人、任意两块交换；本项目是双人、仅允许与空格相邻的方块移动、同局公平竞速。因此不是简单换皮，但实现时必须持续守住这条差异线。

## 2. 调研问题

本轮调研集中回答：

1. 本地 HTML 能否在不上传的前提下读取、解码并裁切用户照片？
2. EXIF 方向、大图解码内存和 Object URL 清理怎样形成安全闭环？
3. 同设备双人竞速怎样保证相同局面、独立输入和可信结算？
4. 没有用户照片时，是否仍能完全离线并直接开始？
5. 键盘、触控、小屏与辅助技术能否共存？
6. 是否需要借鉴或复制开源项目，以及图片权利如何提示？

## 3. 当前仓库边界

### 3.1 已有相邻项目

| 项目 | 已有机制 | 与候选项目的关系 |
| --- | --- | --- |
| `photo-swap-puzzle` | 单块棋盘；选择任意两块交换；本地照片 | 可复用“照片不上传”的产品承诺，但不能复用其任意交换规则作为本项目核心 |
| `panorama-memory` | 本地照片与第三方全景库 | 说明仓库已有较重图片体验；本项目应保持 A 级零外部依赖 |
| `orbit-star-race` | 同设备、同屏双人竞速 | 可对照双人状态呈现，但本项目需要独立棋盘和相同随机局面 |
| `reaction-duel`、`ribbon-tug`、`heart-sprint` | 同设备对抗输入 | 可对照双方输入隔离和胜负反馈，不构成代码借鉴 |

### 3.2 必须守住的产品差异

- 双方看到的是两块独立棋盘，不共享空格位置。
- 双方拿到相同且保证可解的初始排列。
- 每次只能移动空格四邻域中的一块。
- 竞速从同一倒计时结束时开始。
- 用户不选择照片也能用原创内置图直接开局。

## 4. 本地照片：能力与约束

### 4.1 文件选择不会自动上传

HTML 的 `input[type=file]` 会在用户主动选择后提供 `FileList`；`accept` 只是给文件选择器的提示，不能替代运行时校验。读取到 `File` 并不等于发生网络上传，是否联网取决于页面后续是否调用网络能力。

实现门槛：

- 仅接受 JPEG、PNG、WebP，并同时检查 MIME、解码结果和尺寸。
- 不设置表单提交，不实现上传、分享或下载。
- 不调用 `fetch`、XHR、WebSocket、Service Worker。
- 不写入 `localStorage`、`sessionStorage`、IndexedDB 或 Cache Storage。
- 不在 DOM、日志或存储中展示或持久化原文件名。

来源：

- [WHATWG HTML：File Upload state](https://html.spec.whatwg.org/multipage/input.html#file-upload-state-(type=file))
- [W3C File API](https://www.w3.org/TR/FileAPI/)

### 4.2 解码、EXIF 方向与裁切

推荐主路径：

1. 用户选择 `File`。
2. 用 `createImageBitmap(file, { imageOrientation: "from-image" })` 解码。
3. 使用解码后位图的 `width`、`height` 判定实际方向和尺寸。
4. 从中心裁成正方形，并降采样到最长 1200×1200。
5. 画入 Canvas，随后用 `canvas.toBlob("image/jpeg", 0.9)` 生成游戏专用 Blob。
6. 在 `finally` 中调用 `ImageBitmap.close()`。

`imageOrientation: "from-image"` 的默认语义是采用图片元数据给出的方向；CSS Images 也定义了按元数据方向显示后的自然尺寸。不过这是浏览器能力门槛，不能把“规范存在”误写为“任何浏览器都可靠支持”。首版不引入自写 EXIF 解析器：若标准解码路径不可用或失败，保留原创内置图并提示当前浏览器不支持这张自定义照片。

来源：

- [WHATWG HTML：ImageBitmap](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html)
- [CSS Images Module Level 3：image orientation](https://www.w3.org/TR/css-images-3/#the-image-orientation)
- [WHATWG HTML：Canvas](https://html.spec.whatwg.org/multipage/canvas.html)

### 4.3 大图不是只看文件大小

压缩文件很小，也可能解码成极大的像素缓冲区。以 RGBA 粗略估算，2400 万像素单份原始缓冲约为 96 MB；解码源、Canvas、输出和浏览器中间副本同时存在时，峰值会明显更高。

建议首版限制：

- 文件大小不超过 20 MiB。
- 短边至少 600 px。
- 任一边不超过 6000 px。
- 总像素不超过 2400 万。
- 游戏派生图固定不超过 1200×1200。

这些限制是产品保护线，不是内存占用的绝对保证。实现应尽快关闭 `ImageBitmap`、复用单份派生图，并避免为左右棋盘各生成一份完整图片。

### 4.4 Blob URL 生命周期

Object URL 会维持 Blob 的可访问映射；规范明确允许显式 `revokeObjectURL()`，也建议不再需要时及时释放。文档卸载会清理该文档创建的 Blob URL，但产品仍应主动管理，不能只依赖卸载。

建议生命周期：

- 两块棋盘共享同一个派生 Blob URL。
- 替换照片采用“两阶段替换”：新图完整校验并生成成功后，再切换引用。
- 旧图先从所有元素上解除引用，再调用 `URL.revokeObjectURL(oldUrl)`。
- “恢复内置图”、再次换图、`pagehide` 和 `beforeunload` 都调用幂等清理函数。
- 失败的新候选图不影响当前可玩图片。

来源：

- [W3C File API：Blob URL 与生命周期](https://www.w3.org/TR/FileAPI/)

### 4.5 隐私承诺的准确说法

可以承诺：

- 照片仅在当前浏览器页面内处理。
- 项目自身不上传、不保存、不分享照片。
- 重新编码后的游戏图片不主动继承原文件的 EXIF/GPS 元数据。

不应过度承诺：

- 不宣称提供取证级元数据擦除。
- 不宣称浏览器、扩展程序、操作系统或用户另行截图绝对无法取得内容。
- 不把“本地点开”写成图片权利豁免。

## 5. 公平竞速协议

### 5.1 相同且可解的初始局面

不从 9! 排列中盲抽。推荐从完成态出发执行固定次数的合法空格移动：

- 使用本局种子生成 96 次合法移动。
- 禁止立即走回上一步，减少无效抖动。
- 若最终仍是完成态，或曼哈顿距离小于 12，则换种子重试。
- 生成一次排列，再复制给左右双方。

这样天然保持可解，并能通过“同一种子得到同一排列”的纯逻辑测试验证公平性。双方棋盘状态之后完全独立。

### 5.2 输入隔离

- 左方：W/A/S/D。
- 右方：方向键。
- 方向语义统一为“空格移动方向”。
- 忽略 `KeyboardEvent.repeat`，避免按键长按频率差异决定胜负。
- 触控和鼠标：点击空格相邻的原生按钮方块。
- 不实现拖拽，也不使用 `touch-action: none`。
- 倒计时前、暂停时和结算后均拒绝移动。

### 5.3 计时和近同时完成

计时使用 `performance.now()`，因为它是单调时钟，不会因系统时间校准倒退。显示精度只到 0.1 秒，不制造浏览器无法保证的“毫秒级公平”印象。

结算协议：

- 第一方完成时记录单调时间戳，并锁住该方棋盘。
- 开启 100 ms 结算窗口，另一方仍可完成。
- 另一方在窗口内完成则判为“十分之一秒内并列”。
- 超过窗口则第一方获胜。
- 若双方在同一事件循环检查中都已完成，按完成时间戳应用同一规则。

100 ms 是明确的产品规则，不是声称测得了绝对同时。

来源：

- [W3C High Resolution Time Level 3](https://www.w3.org/TR/hr-time-3/)

### 5.4 切后台与失焦

后台页面可能降低计时器和渲染频率。倒计时或比赛中遇到 `visibilitychange` 变为 hidden，或窗口失焦时，应暂停双方并冻结有效用时；用户显式恢复后重新进行短倒计时，再继续同一局。禁止在后台“补跑”倒计时。

来源：

- [WHATWG HTML：Page Visibility](https://html.spec.whatwg.org/multipage/interaction.html#page-visibility)

## 6. 原创内置图与零依赖

首屏必须在没有用户照片时就能完整开局。内置图建议由页面代码在 Canvas 上绘制原创抽象画面，例如两颗不同颜色的行星、轨道、星点和明显的九宫格定位细节：

- 不下载第三方图片。
- 不内嵌来源不明的 Base64 素材。
- 不依赖字体、图标库、CDN 或 ES Module。
- 生成后走与用户照片相同的派生图片和拼图渲染路径。

这样既是隐私兜底，也是 `file://`、离线和版权验收的稳定样本。

## 7. 图片权利与借鉴声明

美国版权局说明，游戏的思想、标题和玩法方法本身通常不受版权保护，但规则文本和美术表达可能受保护；摄影作品的创作性选择受保护，摄影师通常是初始权利人。

产品提示应写明：

- 仅选择自己拍摄、已获授权或有权使用的照片。
- 本地处理不会改变照片的权利归属。
- 内置图为本仓库原创、由代码生成。

本项目调研和方案为**独立实现**，未选择任何开源滑块拼图项目作为代码、视觉或素材参考，也不计划复制第三方规则文本。实现阶段若事实发生变化，必须在项目 README 的“借鉴声明”中逐项列出项目名、链接、许可证、借鉴范围和具体改写；在此之前不得泛化声称“参考互联网实现”。

来源：

- [U.S. Copyright Office：Games](https://www.copyright.gov/register/tx-games.html)
- [U.S. Copyright Office Circular 42：Copyright Registration of Photographs](https://copyright.gov/circs/circ42.pdf)

## 8. 可访问性、触控与响应式

### 8.1 交互语义

- 每个可见方块使用原生 `button`。
- 按钮名称包含原图行列、当前行列以及是否可移动。
- 棋盘用带标题的 `section` 或 `group` 表达，不在首版强行套用 ARIA `grid`。
- Tab 可逐个聚焦，Enter/Space 可激活；W/A/S/D 与方向键只是快捷键。
- 局面开始、暂停、恢复、领先、完成和胜负通过 `aria-live="polite"` 宣告。
- 焦点环至少 2 px 且与背景高对比。

WAI-ARIA Grid 是复合组件，采用后就要自行管理单一 Tab 停靠点和方向键导航。本项目右方方向键本身就是比赛操作，首版使用原生按钮更清晰，也避免制造两套相互冲突的方向键语义。

### 8.2 指针与动画

- 方块目标尽量保持至少 44×44 CSS px，高于 WCAG 2.2 的 24×24 最低目标。
- 点击动作在抬起前可取消，不在按下瞬间不可逆地执行。
- 不要求拖拽完成任何功能。
- `prefers-reduced-motion: reduce` 下关闭方块位移动画和倒计时缩放，不改变规则与反馈。

### 8.3 小屏公平性

比赛时两块棋盘必须同时可见，不能在窄屏把一方堆到另一方下方。建议：

- 桌面端双列，棋盘按可用空间放大。
- 390 px 和 320 px 宽度仍保留双列，缩小间距、标题和装饰。
- 320 px 下每块棋盘约 144 px，单格仍可接近 48 px。
- 操作说明放在棋盘上方；比赛区不产生横向滚动。
- 不禁用页面缩放，不设置 `user-scalable=no`。

来源：

- [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- [WAI-ARIA Authoring Practices：Grid Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)

## 9. `file://` 可行性

项目可以保持 A 级：

- 入口为相对路径静态 HTML。
- 脚本使用经典相对 `<script src>`，不依赖模块加载器。
- 文件选择、Canvas、Blob 和 Object URL 都是页面内能力。
- 默认图不需要网络。

但最终验收必须分三层：

1. 静态检查证明无远程依赖、无网络 API、无存储 API。
2. 在本地 HTTP 测试环境完成自动化交互和响应式测试。
3. 人工从文件管理器双击 `index.html`，完成一次默认图比赛和一次本地照片比赛。

自动化浏览器若因控制策略不接受 `file://`，只能记录为测试工具边界，不能用 HTTP 成功替代人工双击证明。

## 10. 风险矩阵

| 风险 | 级别 | 控制措施 | Go 门槛 |
| --- | --- | --- | --- |
| 与 `photo-swap-puzzle` 过近 | 中 | 双棋盘、严格邻接、相同局面竞速 | 规格和验收都能清楚区分 |
| 图片方向错误 | 中 | `createImageBitmap` 的 `from-image`；失败保留默认图 | 横竖方向样例通过 |
| 大图导致内存峰值 | 高 | 文件、边长、像素三重上限；及时 `close` 与 revoke | 超限、失败路径不破坏当前局 |
| Blob URL 泄漏 | 中 | 单 URL 共享；两阶段替换；幂等清理 | 自动化 spy 与重复换图通过 |
| 键盘长按不公平 | 中 | 忽略 repeat；每次 keydown 最多一步 | 逻辑与浏览器测试通过 |
| 切后台仍计时 | 中 | hidden/blur 同时暂停；显式恢复倒计时 | 可重复验证 |
| 小屏一方不可见 | 高 | 320 px 仍并排且无横向滚动 | 320/390 截图与尺寸断言通过 |
| 用户误用无权照片 | 中 | 权利提示；不提供上传分享 | 提示可见且不夸大 |

## 11. Go / Conditional / No-Go

最终建议为 **Go**，原因：

- 核心能力均可由本地浏览器标准能力完成。
- 可做成真正零上传、零持久化、零第三方运行时依赖。
- 与现有单人任意交换拼图有可验证的机制差异。
- 同设备双人公平性可以通过冻结协议和纯逻辑测试控制。

以下任一情况会把实现验收降为 **Conditional**：

- 无法在目标浏览器可靠处理照片方向。
- 320 px 下不能让双方棋盘同时可见并满足触控目标。
- 后台暂停或 100 ms 并列规则无法稳定测试。
- 替换照片后存在未释放 Object URL。

以下任一情况为 **No-Go**：

- 需要上传用户照片或依赖远程服务才能开始。
- 默认体验依赖无权使用的第三方图片。
- 最终交互退化为现有 `photo-swap-puzzle` 的双份复制，而非严格滑块竞速。
