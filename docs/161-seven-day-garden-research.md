# A 级“把七天，养成一朵花”定向调研

调研日期：2026-07-21

对应创意：`C16 七日小花园`

建议目录：`experiences/co-op/seven-day-garden/`

建议等级：A（单设备轮流、`file://` 直开、无第三方运行依赖）

## 1. 调研结论

这个题目适合实现成一段七日公开规划合作：两个人各有一篮固定数量的浇水、补光和修剪卡；每天双方各出一张，合起来满足当天花签，同时不能把后面几天必需的卡提前用光。

正式方向采用 **两个工具篮的七日精确覆盖**：

- 七天花签、两篮库存和行动顺序全部固定，不使用随机、真实日期或长期等待；
- 每天两席各行动一次，首行动席逐日交换，七天后双方各行动 7 次；
- 当天两张卡的无序对必须满足花签；满足今天但使后缀无解时，明确提示“后面会少一张卡”；
- 失败归还当天两张卡，只重试当天，已经养成的日期形成不可回退前缀；
- 完成页只记录七天共同照料，不排名、不比较谁贡献更多；
- 规则由纯 reducer 与有限状态求解器证明，页面只渲染公开 view。

这比三个资源仪表更容易在 30 秒内讲清，也和现有实时同步、双边界、配电平衡、私密线索及记忆接力样板保持机制差异。

## 2. Brainstorm：四个方向与取舍

### 方向 A：真实七天的长期植物

让玩家每天现实中打开一次页面，七天后开花。它有纪念感，但必须依赖日期、存储、补签和设备时钟；用户无法一次玩完，清理浏览器数据后也会失去进度。

**结论：不采用。** “七日”是七个离散回合，不是七个现实日。

### 方向 B：水分、光照、冠幅三仪表

两人轮流给数值加减，维持植物七天存活。这种方向更像模拟，但要解释上限、消耗和天气修正；视觉容易退化成资源控制台，也与“月面，保持有光”的多指标安全平衡接近。

**结论：不采用。** 保留园艺动作，去掉连续仪表。

### 方向 C：双方各持一半秘密线索

一人看叶片提示、一人看土壤提示，口述后决定当天组合。它能证明认知合作，但需要隐藏交接和码表，明显靠近“把信号接回来”“雾里，跟着你走”已有的私有视图/口述解码。

**结论：不采用。** C16 的信息和计划全部公开。

### 方向 D：两篮有限卡的七日精确覆盖

每席拥有不同但公开的固定卡量，每天各出一张。当前花签只约束今天的工具对，有限库存又要求双方提前讨论后六天；生产求解器可以在每次日结时检查剩余后缀是否仍有解。

**结论：采用，进入规格冻结。**

## 3. 冻结候选规则

### 3.1 七日花签

工具代号：`W = 浇水`、`S = 补光`、`P = 修剪`。花签只要求无序对，席位分配由两篮库存决定。

| 日 | 花签 | 需求对 | 叙事作用 |
| --- | --- | --- | --- |
| 1 | 醒土 | `WS` | 一边润土，一边迎光 |
| 2 | 扶芽 | `WP` | 给新芽水，也给它留出形状 |
| 3 | 展叶 | `SS` | 两份光让叶面舒展 |
| 4 | 定枝 | `SP` | 光照与修剪共同定下方向 |
| 5 | 蓄水 | `WW` | 两边一起为花期储水 |
| 6 | 整冠 | `PP` | 两次修剪完成花冠轮廓 |
| 7 | 开花 | `WS` | 最后一份水与光让花开放 |

### 3.2 两只工具篮

| 席位 | 浇水 `W` | 补光 `S` | 修剪 `P` | 合计 |
| --- | ---: | ---: | ---: | ---: |
| 席位 A | 3 | 1 | 3 | 7 |
| 席位 B | 2 | 4 | 1 | 7 |

两篮总量精确等于七日总需求：`W5 + S5 + P4 = 14`。接受一天后才真正扣卡；失败重试恢复到当天开始的库存。

### 3.3 唯一完整路线

对每一天枚举 A/B 各三种选择，过滤库存不足与花签不匹配，再递归搜索后缀。完整搜索空间上界仅为 `9^7`，按库存状态记忆化后更小。

独立穷举结果：完整席位分配 **恰好 1 条**。

| 日 | A | B |
| --- | --- | --- |
| 1 | `W` | `S` |
| 2 | `P` | `W` |
| 3 | `S` | `S` |
| 4 | `P` | `S` |
| 5 | `W` | `W` |
| 6 | `P` | `P` |
| 7 | `W` | `S` |

唯一解不应直接显示给玩家。页面公开七日花签和双方剩余卡，让两个人一起规划；若今天组合正确但会使后缀解数归零，只说明“今天够了，但后面会少一张卡”，不替玩家指出应由谁改牌。

## 4. 状态机与裁决草案

建议阶段：

1. `intro`：题名、规则与两篮预览；
2. `day-intro`：当天花签和剩余七日计划；
3. `handoff`：公开花园保留，只显示当前席位与接手动作；
4. `choosing`：当前席位从自己的剩余卡选择一张；
5. `day-result`：花签满足且后缀仍可解，植物长出当日部分；
6. `jammed`：`pair-mismatch` 或 `future-stranded`，归还当天卡并重试；
7. `complete`：七天、14 张卡和成熟植物的共同记录。

候选动作：`START`、`BEGIN_DAY`、`TAKE_OVER { seat }`、`CHOOSE { seat, tool }`、`RETRY`、`NEXT_DAY`、`RESTART`。交接不是秘密遮屏：花签、两篮、已选卡和植物状态都属于共享信息；`handoff` 只防止连续误触并明确现在由谁操作。

生产 evaluator 在第二席选牌后返回：

- `pair-mismatch`：两张卡不等于今日需求对；
- `future-stranded`：今天匹配，但扣卡后 `countSuffix(...) === 0`；
- `accepted`：今天匹配且后缀仍有至少一条路线。

所有 9 种有序工具组合必须由同一个生产 evaluator 处理，UI 不复制规则。

## 5. 合作必要性与确定性证明

对合作必要性：

1. 每天成功谓词要求两个不同席位各有一张 commitment；
2. 席位只能消耗自己的库存，不能替另一篮出牌；
3. 每席每天最多行动一次，重复席位和伪造 turn 都是 no-op；
4. 任一席不行动时，当天二元需求永远无法结算；
5. 所以任一席位都不能独自完成一天，更不能完成七日路线。

同机作品无法识别现实中是否真有两个人；规则能证明的是两份席位权限都不可缺少。README 必须诚实写明这一信任边界，不加入摄像头、账号或身份识别。

对确定性：

- 同一初态、配置与 action 序列必须得到相同结果；
- 不读取 `Date`、真实时间、随机数、网络、存储或动画帧；
- `countSuffix` 只接受规范化日序与两篮整数库存；
- accepted days 必须始终是冻结七日表的严格前缀；
- JSON action log 能重放到深度相等状态；
- 第七日后只允许进入 `complete`，不存在第八日。

## 6. 本地实现可行性

- 纯 HTML、CSS 与经典脚本 `config.js → logic.js → app.js`；
- 零第三方运行库、零服务、零请求、零存储、零音频和零真实时钟；
- `config.js` 只允许定制两席称呼与完成结语，不能覆盖七日花签、库存或 solver；
- 规则层为 CommonJS/浏览器双出口纯 reducer，可直接在 Node 测试全部前缀、9 种日组合和唯一路线；
- 植物、叶形日历、花签、卡量、席位和反馈由公开 view 驱动；
- 图片只承担窗边花桌、盆栽材质和完成纪念插画，损坏时仍保留可玩的 DOM/CSS 植物轮廓；
- 双击 `index.html` 即可完整游玩，因此属于 A 级。

## 8. 视觉与交互方向

核心画面必须是一盆持续变化的植物，而不是 7 行 × 3 列资源表：

- 桌面照料态：清晨窗边园艺桌，植物居中，两侧工具篮等权，七片叶形日历形成顶部进度；
- 移动交接态：花园继续可见，一张纸签提示当前席位接手；确认后露出自己的三类卡；
- 完成态：成熟植物与摊开的七日压花日志，七片叶印记录七次共同日结；
- 三类工具用真实园艺物件语义和大型原生按钮表达，不能只用颜色或单字母；
- 数量可以作为小标签，但不能变成主视觉仪表；
- 生成图片只做背景、植物材质和完成纪念物；日序、库存、花签、席位、卡牌、结果与可访问名称全部代码原生。

## 9. 浏览器与可访问性标准

- Pointer 输入遵循 W3C [Pointer Events](https://www.w3.org/TR/pointerevents3/)，每次点击只提交一张离散照料卡；
- 阶段与状态更新使用原生 button、heading、list、status 等语义，以 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 为基线；
- 390×844 依次显示日期/席位、植物、花签、当前篮与三个工具按钮；
- 320×568 允许必要纵向滚动，工具按钮保持至少 56px 高；
- 状态同时用叶片形态、图标和文字表达，不能只靠绿色/黄色/红色；
- `aria-live="polite"` 只播报接手、选牌、日结、重试和完成，不播装饰动画；
- `prefers-reduced-motion` 关闭叶片舒展等表现动画，不改变日结；forced-colors 保留系统边框与文字；
- 本作没有实时规则，不应启动 `requestAnimationFrame` 规则循环。

## 10. 风险与进入规格的 Gate

| 风险 | 规格前必须冻结的处理 |
| --- | --- |
| 唯一解变成死记答案 | 从首屏公开七日花签与两篮库存，玩法定位为共同规划；失败解释后缀资源，不泄露正确席位 |
| `future-stranded` 看起来黑箱 | 文案明确“今天够了，但后面会少一张卡”，测试证明生产 solver 与验收 oracle 同源 |
| 第二席只按第一席补牌 | 这是公开合作而非秘密猜测；挑战在于跨七日分配，不增加无依据遮挡 |
| 一个人操作两席 | 明确同机信任边界；规则证明席位不可替代，不做身份监控 |
| 页面退化成库存表 | 植物始终占主视觉，库存只用工具篮和可取卡表达 |
| 动画反过来决定生长 | 日结状态先确定，动画只呈现 accepted day；降动效时结果不变 |
| 第七日后仍能行动 | 完成阶段拒绝所有出牌；测试不存在第八日与库存负数 |
| 开源园艺素材许可混乱 | 生产资产只用纯文字 ImageGen 原创生成，不引入审阅仓库素材 |
