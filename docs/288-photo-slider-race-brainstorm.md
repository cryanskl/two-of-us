# Photo Slider Race Brainstorm

## 1. Brainstorm 目标

基于 `287-photo-slider-race-research.md` 的 Go 结论，为“情侣或两人本地点开即玩”的照片滑块项目选择一个首版方向，并明确哪些有吸引力但会损害公平性、离线性或最小实现的想法暂不进入规格。

冻结前提：

- 项目 ID：`photo-slider-race`
- 推荐名：**同一张，谁先拼回**
- `versus` / A 级
- 同一设备、同一屏幕、两人同时玩
- 3×3 严格滑块规则
- 原创内置图可立即开始
- 可选本地照片；不上传、不保存
- 独立实现，不复制开源项目代码、素材或规则文本

## 2. 三个可行方向

### 方向 A：镜像公平竞速

双方拥有独立棋盘，但开局排列完全相同，同时倒计时，同时开始。最先复原的一方获胜，100 ms 内完成则并列。

体验句：

> 同一张回忆、同一个乱序，看看谁先把它拼回来。

优势：

- 一眼就能理解公平性。
- 两人全程同时参与，没有等待。
- 同一局面使胜负更多来自观察与操作，而不是随机难度。
- 很适合自定义情侣照片，情感主题自然但不影响玩法。
- 可用键盘分区，也可双方直接点自己的棋盘。

风险：

- 320 px 小屏仍要并排两块棋盘，对布局要求高。
- 双方会互相看到对方进度，可能跟随对方路径。
- 需要精确定义近同时完成、后台暂停和按键重复。

控制：

- 固定 3×3，不在首版增加难度选择。
- 双方棋盘保持独立，状态不互相影响。
- 以 100 ms 并列窗口承认设备调度精度边界。
- 允许看到对方进度，把它视为同屏对抗的一部分；因为局面相同，信息暴露也是对称的。

### 方向 B：一图两半接力

一张照片被拆成左右两个区域，第一人完成左半后第二人才能开始右半，记录总时间。

体验句：

> 我先拼好我们的左半边，再把右半边交给你。

优势：

- 情侣叙事更明显。
- 一台手机轮流操作很自然。
- 单块棋盘可做得更大。

风险：

- 一半时间有人在等待，不是同时对抗。
- 两半图像纹理难度不一致，接力时间不能直接比较。
- “滑块拼图的半张图”容易出现边界和空格规则歧义。
- 更接近合作/接力，不符合本轮“双人进行对抗”的目标。

结论：可作为以后独立项目，不进入本项目首版。

### 方向 C：共享棋盘抢步数

双方操作同一块棋盘，左方和右方轮流移动；完成时根据有效步数或最后一步判胜。

体验句：

> 我们一起拼，但最后一块算谁的？

优势：

- 只有一块棋盘，小屏适配容易。
- 既有合作又有轻对抗。
- 局面变化会产生讨论。

风险：

- 玩家目标冲突：想完成还是想抢最后一步？
- 一方可以故意走坏局面，规则容易变成争吵源。
- 轮流、超时、无效步和撤销都需要额外规则。
- 不是“同局面独立竞速”，无法用完成时间做清晰结算。

结论：趣味性存在，但不适合这个项目的首版承诺。

## 3. 决策

选择 **方向 A：镜像公平竞速**。

决策理由按优先级排序：

1. 最符合“两个人一起玩、进行对抗”。
2. 同一初始排列形成可解释、可测试的公平。
3. 一局无需教程即可理解。
4. 本地照片为体验增加情感，而不是成为必填配置。
5. 在完全离线、无依赖条件下仍可稳定完成。

不混合 B 或 C。首版不会增加合作接力、共享棋盘、道具干扰、在线房间或排行榜。

## 4. 核心体验节奏

### 4.1 首次打开

页面首屏展示：

- 项目名和一句规则。
- 一张由代码生成的原创内置图。
- “开始比赛”主按钮。
- “换成我们的照片”次按钮。
- 简短隐私提示：“只在当前页面处理，不上传、不保存。”
- 双方键位提示：左方 W/A/S/D，右方方向键。

默认图已经足以开始，不出现强制上传步骤。

### 4.2 准备

点击开始后：

1. 生成一个可解且不太接近完成态的排列。
2. 把同一排列复制到左右棋盘。
3. 双方棋盘同时显示。
4. 播放 3、2、1 倒计时。
5. 倒计时结束后同时解锁输入并开始计时。

### 4.3 比赛

- 双方可以看见自己的移动次数、状态和另一方进度。
- 键盘每次按下最多移动一步；按住不连发。
- 指针点击只有相邻方块会移动。
- 不合法输入没有惩罚，只给轻微视觉提示；减少误触造成的争议。
- 方块移动使用短动画；减少动态偏好下直接切换。

### 4.4 完成

第一方完成后：

- 该方棋盘立刻锁定并显示完成状态。
- 另一方仍有 100 ms 结算机会。
- 最终显示左方胜、右方胜或“十分之一秒内并列”。
- 展示双方用时和步数；未完成方显示结算时的进度，不伪造完成用时。

主要后续动作：

- “同一局面再来一场”：保持图片，生成新的双方相同排列。
- “换一张照片”：回到准备状态，比赛中不允许换图。

不提供成绩保存或历史排行榜。

## 5. 情感表达方向

本项目的情感来自“共同照片”和“同一份回忆”，不通过大量文案强行煽情。

推荐语气：

- 轻松、亲密、有一点挑战。
- 胜负反馈不嘲讽。
- 并列被当作有趣结果，而非错误。

可用文案草案：

- 标题：同一张，谁先拼回
- 副标题：同一张回忆，同一个乱序。三、二、一——开拼。
- 照片按钮：换成我们的照片
- 默认按钮：用这张先比一局
- 左方：左边的你
- 右方：右边的你
- 并列：十分之一秒内，同时拼回来了
- 隐私：照片只在这个页面里处理，不上传，也不保存

避免：

- “证明谁更爱谁”之类把胜负和感情绑定的文案。
- “绝对安全”“绝不泄露”等超范围隐私承诺。
- 失败方羞辱、惩罚或强制分享。

## 6. 视觉方向

### 6.1 整体

视觉关键词：

- 深夜蓝紫底色
- 暖金和珊瑚色双玩家标识
- 玻璃感但不依赖模糊可读性
- 照片是主角，装饰退后
- 两块棋盘视觉权重完全对称

避免直接沿用现有项目的具体视觉构图。颜色、图形和默认图均独立设计。

### 6.2 原创默认图

默认图由 Canvas 代码绘制：

- 深蓝星空渐变背景。
- 左下暖金行星与右上珊瑚行星。
- 两条交错但不重合的轨道。
- 九宫格各区域都有可辨认的星点、光斑或轨道切线。
- 中心有一枚小小的双星符号，完成后才形成完整图案。

它既要好看，也要为拼图提供足够的定位线索。不能只做大片纯色渐变，否则玩法难度来自猜测而不是观察。

### 6.3 双方识别

- 左方使用暖金强调色。
- 右方使用珊瑚强调色。
- 颜色之外同时使用文字“左方/右方”和不同的简单几何徽记。
- 胜负状态同时靠文本、边框和图标表达，不只变色。

## 7. 输入方案比较

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 左 WASD / 右方向键 | 双方可同时操作；传统；易测试 | 笔记本方向键区域可能较小 | 采用 |
| 左点击 / 右点击 | 手机自然；无需键盘 | 两人手指可能互相遮挡 | 作为同等入口 |
| 拖动方块 | 直觉较强 | 拖拽取消、触屏滚动和无障碍复杂 | 不采用 |
| 轮流聚焦后用方向键 | 键位少 | 不是同时竞速；焦点争用 | 不采用 |
| 同一键位按左右半屏 | 手机可同时按 | 无法完整表达四个方向 | 不采用 |

方向键语义统一为“空格向该方向移动”。页面要在赛前明确展示，不使用“方块向哪移动”这一容易相反理解的说法。

## 8. 难度与随机性

首版只做 3×3：

- 2×2 太短，胜负受一次误触影响过大。
- 4×4 在双棋盘小屏上过密，触控和可读性都变差。
- 难度选择会扩大状态和验收矩阵，不是首版必需。

随机性只决定起始排列，不决定双方难度。理想局面：

- 不是完成态。
- 曼哈顿距离至少 12。
- 由合法移动生成，保证可解。
- 同一场双方完全一致。
- “再来一场”产生新局，但调试模式可以固定种子复现。

## 9. 暂不做清单

- 联网对战、二维码房间、跨设备同步。
- 后端、账号、排行榜、战绩存储。
- 照片上传、云备份、下载或社交分享。
- AI 图片分析、自动识别人脸、情感文案生成。
- 4×4、5×5 或自定义难度。
- 道具、干扰、时间惩罚、提示、自动完成。
- 背景音乐和远程音频。
- 拖拽操作。
- 多张照片相册。
- 读取原文件名、拍摄时间、GPS 或其他 EXIF。
- 引入第三方拼图库、手势库或图片处理库。

这些想法只有在首版完成并验证后，才能作为独立增强重新讨论。

## 10. 边界场景

### 10.1 照片失败

- 格式不支持：说明支持 JPEG/PNG/WebP，继续保留当前图。
- 文件过大或尺寸超限：给出明确上限，继续保留当前图。
- 解码失败：说明无法读取，不清空当前图。
- 浏览器缺少所需解码能力：提示可继续用内置图。
- 快速连续选择：只有最后一次有效解码结果可以替换当前图，旧任务结果不得回写。

### 10.2 对局中断

- 切换标签页、最小化或失焦：双方同时暂停。
- 恢复后：显示短倒计时，再继续。
- 页面缩放或旋转：棋盘重新布局，但不重置局面。
- 刷新或关闭：局面丢失，这是零持久化的预期行为。

### 10.3 输入冲突

- 焦点在文件输入或普通按钮时，不把键盘当作比赛移动。
- 比赛激活后 W/A/S/D 和方向键移动各自棋盘，同时阻止这些键造成页面滚动。
- Tab、Enter、Space 保留原生按钮行为。
- `event.repeat` 一律忽略。

## 11. 可访问性构想

首版不以复杂 ARIA 棋盘组件为目标，而是让原生控件真正可用：

- 每块图块都是 `button`。
- 空格不伪装成无名称按钮。
- 按钮名称说明“原图第几行第几列，现在位于第几行第几列，可/不可移动”。
- 左右棋盘有独立标题和简短操作说明。
- 计时与结果可见，同时通过礼貌型 live region 宣告。
- 焦点环始终可见。
- 减少动态时不做滑行动画。
- 不以颜色作为唯一状态信息。

## 12. 成功标准

一次成功的首版体验应满足：

1. 用户双击 HTML 后，不选照片即可在 10 秒内开始。
2. 两人能在同一屏幕上同时操作，且不会串到对方棋盘。
3. 双方起始排列逐格一致，并且一定可解。
4. 用户能明确理解移动方向和胜负规则。
5. 换照片失败时，当前体验不被破坏。
6. 关闭页面后项目没有留下照片或成绩。
7. 320 px 宽度仍能同时看到双方棋盘并点击图块。
8. 项目 README 清楚说明独立实现和图片权利要求。

## 13. Brainstorm 决策记录

| 决策 | 选择 | 排除项 |
| --- | --- | --- |
| 核心玩法 | 两块独立棋盘公平竞速 | 接力、共享棋盘 |
| 棋盘 | 固定 3×3 | 难度选择 |
| 开局图片 | 原创 Canvas 内置图 | 第三方默认素材 |
| 自定义图片 | 单张本地 JPEG/PNG/WebP | 相册、上传 |
| 双人输入 | 左 WASD、右方向键、双方可点击 | 拖拽、轮流焦点 |
| 结算 | 首位完成；100 ms 内并列 | 毫秒排名、加时道具 |
| 数据 | 当前页面内存 | 战绩持久化、排行榜 |
| 实现来源 | 独立实现与 Web 标准 | 复制开源拼图 |

下一阶段的 spec 应把上述选择转成状态机、数据模型、错误契约和逐条验收标准，而不是继续扩展创意。
